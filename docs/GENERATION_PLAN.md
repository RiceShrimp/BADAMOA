# 데이터 생성 · 증강 계획 — 이미지 속성 증강부터

ROADMAP의 Phase 7(Build: 데이터 생성)을 구체화한다. 첫 기능은 NVIDIA [Cosmos Data Factory](https://github.com/NVIDIA/cosmos-data-factory)의 **Image Attribute Augmentation**(이하 IAA)과 같은 일을 BADAMOA 안에서 하는 것이다.
아직 구현 전이다(2026-11-19 계획).

## 1. IAA가 하는 일

참고: [cdf-image-attribute-augmentation SKILL.md](https://github.com/NVIDIA/cdf-orchestration/blob/main/skills/cdf-image-attribute-augmentation/SKILL.md) (v1.0.1)

- **사람 크롭의 옷 · 색 · 신발 같은 속성을 이미지 편집 모델로 바꿔**, 같은 사람의 다른 차림 이미지를 만들고 속성 설명을 붙인다. 목적은 **사람 검색 · 재식별(re-ID)** 학습 데이터를 늘리는 것이다.
- 날씨 · 시간대 · 조명을 바꾸는 기능이 아니다. 그건 같은 프로젝트의 **Video Data Augmentation**(Cosmos Transfer)이다(4장의 다음 단계).
- 원본의 흐름:
  1. 입력 준비: 사람 ID별 폴더의 크롭을 한 사람당 가로 띠 하나로 묶음
  2. 이미지 편집(Cosmos image-edit 서비스)으로 속성을 바꾼 변형을 만듦
  3. 후처리
  4. 사건 · 사람 속성 검색(VLM이 속성 캡션과 검색어를 만듦)
  5. 증강 데이터셋 생성(`augmented_data.json`)
  6. 결과 받기
- 확인: 속성 확인 검사(attribute verification, Cosmos Evaluator)를 켜고 끌 수 있다. "작업이 성공 = 모든 결과가 좋음"이 아니라는 점을 따로 보고한다.
- 모델: VLM(Qwen 계열 — 캡션 · 속성 · 확인)과 이미지 편집 서비스. **외부 엔드포인트 모드**(이 쪽은 GPU 0장)와 **내부 배포 모드**(GPU 2장 이상: VLM 하나 · 편집 하나)가 있다.
- 주요 설정: `num_augmentation`(사람마다 변형 수, 기본 1), `max_imgs`(처리할 사람 수, 0 이하 = 전부), `variable_distribution`(바꿀 속성 6개와 그 값의 분포 파일).
- 원본은 Kubernetes + Airflow + S3, NGC API 키와 Hugging Face 토큰이 필요하다. 코드 Apache-2.0, 문서 CC-BY-4.0. **모델의 라이선스(상업 이용)는 따로 확인해야 한다.**

### 1.1 Cosmos 쪽 흐름 (참고)

참고: [NVIDIA Cosmos Opens New Tools to Train, Evaluate and Deploy World Models](https://blogs.nvidia.com/blog/cosmos-open-train-evaluate-deploy-world-models/) (2026-10-21)

- **Cosmos 3 · Cosmos 3 Nano**: 열린 월드 모델. Nano는 작게 줄인 변형이고 Hugging Face 컬렉션과 적응용 코드가 함께 있다. 12 GB급 노드에서 직접 띄울 후보는 Nano 쪽뿐이고, 그것도 VRAM은 확인이 필요하다.
- **Cosmos Data Factory**: 라벨링 · 큐레이션 · 증강 · 평가 도구와 스킬, 청사진 다섯 가지.
  - 이미지 속성 증강 — "물체의 겉모습을 바꿔 이미지 검색을 좋게"
  - 영상 증강 — 장면 구조를 지키며 날씨 · 조명을 바꿈
  - 결함 이미지 생성(PCB · 금속 · 유리)
  - 이벤트 영상 생성
  - 자율주행 데이터셋 생성
- **Cosmos Curator**(영상 큐레이션), **Cosmos Framework**(파인튜닝 · 강화학습 · 증류 · 양자화 · 배포).
- **Cosmos 3 NIM**: NGC의 컨테이너로 배포한다(사내 GPU에도). 엔드포인트 방식(2장의 A)의 후보다.
- 사례: Ultralytics가 실제 이미지에 합성 결함을 더해 YOLO를 다시 학습해 결함 위치 찾기와 재현율이 좋아졌다고 한다. 우리 A/B(2장 마지막 줄)와 같은 방식이다.
- 이 글에는 라이선스(가중치 · 코드 · 청사진의 상업 이용), VRAM, 라벨(박스 · 마스크 · 점)을 편집 뒤에 어떻게 이어 가는지가 없다. G0에서 모델 카드와 저장소로 확인한다.
- IAA는 "검색을 좋게"를 겨냥한다. Phase 2의 자연어 이미지 검색(SigLIP2)을 잴 때, 속성 캡션이 붙은 증강 이미지를 검색 시험 세트로 쓸 수도 있다.

## 2. BADAMOA에서의 모양

**쓰임: 사람 속성 분류**(2026-11-19 결정). 검출 데이터의 person 박스를 잘라, 크롭마다 상의 색 · 하의 종류 · 신발 같은 속성을 분류하는 모델을 학습한다. 원본 IAA의 목적(검색 · 재식별)과 달리 사람 ID는 필요 없고, 크롭 하나가 학습 이미지 하나다. 증강은 속성 값이 고르게 퍼지도록 드문 값(예: 빨간 상의)을 늘리는 데 쓴다.

원칙은 그대로다: Hub는 가볍게, 무거운 모델은 노드나 엔드포인트에서, 결과는 **새 데이터셋 버전**(계보로 원본에 이어짐), 사람이 검수한다. Airflow · Kubernetes는 들이지 않는다 — 노드 작업으로 같은 단계를 돈다.

| 단계 | BADAMOA에서 |
|---|---|
| 입력 | 데이터셋 버전에서 거른 이미지(라벨링 묶음 만들기와 같은 필터)와 대상 클래스(person). 노드가 그 박스를 여백을 두고 잘라 크롭을 만든다. 너무 작거나 가려진 박스는 건너뛴다(최소 크기 설정) |
| 원본 크롭의 속성 | 원본 크롭에도 속성 라벨이 있어야 한다. 사람이 달거나, VLM이 먼저 달고(오토라벨과 같은 흐름) 사람이 검수한다 |
| 바꿀 속성 | 관리자가 정한 속성과 값의 분포(예: 상의 색 · 하의 · 신발). 원본의 `variable_distribution`. 이미지당 변형 수와 최대 개수도 고른다 |
| 실행 | 노드 작업 `augment.attributes`. **A. 엔드포인트**: 사내 · 외부 VLM과 편집 서비스(NIM 등) 주소를 관리자 설정에 등록하고 노드가 부른다 — 12 GB급 GPU에서는 이 방식이 현실적이다(ARCHITECTURE 104줄). **B. 노드에서 띄움**: GPU가 충분한 서버("생성용" 역할을 새로 두거나 오토라벨용)에 모델을 띄운다 |
| 확인 | VLM이 편집 결과가 요청한 속성과 맞는지 보고, 맞지 않거나 사람이 깨진 이미지는 버린다. 버린 수와 이유를 보고서로 |
| 출력 | 새 데이터셋 버전(사람 속성 태스크): 원본 크롭과 변형 크롭, 크롭마다 속성 값과 출처(`generated:<생성기> v<버전>`, 원본 이미지 · 프롬프트 · 시드). 변형 크롭의 속성 라벨은 편집에 요청한 값이고, VLM이 확인한 것만 남긴다. 생성한 이미지는 노드의 BADAMOA 저장 위치에 쓰고 그 폴더를 등록한다(지금의 "복사 없이 등록" 그대로) |
| 계보 | 원본 버전 → 증강 실행 → 새 버전. 생성 이미지에는 `synthetic` 표시. 평가 세트는 실제 이미지만 쓴다 |
| 검수 | 생성 이미지를 라벨링 묶음으로 넘겨 사람이 승인 · 버림(LABELING_PLAN 3E). 오토라벨과 같은 보드 |
| 화면 | 버전 화면의 "증강" → 거른 이미지 · 대상 클래스 · 속성 분포 · 개수 · 생성기 · 서버 → 진행 → 결과 버전(원본과 나란히, 속성별 분포 차트) |
| 효과 재기 | 같은 설정으로 "원본만"과 "원본 + 증강"을 학습해 평가 세트(EXTENSION_PLAN 6.4)로 비교한다(A/B) |

생성기(편집 모델 + VLM 묶음)는 모델 종류(템플릿)와 같은 틀로 등록한다. 선언 파일 + 코드에 `generate` 진입점을 두고, 관리자가 시험 실행하고 허용한 것만 쓴다(EXTENSION_PLAN 8장의 흐름).

## 3. 먼저 있어야 하는 것

- **라벨의 속성**: 증강 결과의 속성 값(상의 색 등)을 담을 자리. LABELING_PLAN 3B의 박스 속성, EXTENSION_PLAN의 태스크 속성 · manifest 형식.
- **사람 속성 태스크**: 크롭 하나에 속성 여러 개(속성마다 값 하나)를 담는 라벨. 지금의 분류는 이미지당 클래스 하나라 모자라다. 필요한 것: 속성을 선언하는 팀 태스크(EXTENSION_PLAN 5장의 태스크 등록), 에디터의 속성 입력(LABELING_PLAN 3B), 그걸 학습하는 다중 속성 분류 모델 종류(속성마다 출력 하나), 속성별 정확도 지표.
- **크롭 만들기**: 검출 버전의 person 박스에서 크롭 버전을 만드는 기능(증강 없이도 쓸모 있음 — 사람 속성 데이터의 출발점).
- **생성 이미지를 쓸 곳**: 노드의 쓰기 가능한 저장 위치(EXECUTION_PLAN 4.3의 폴더 접근 점검).
- **평가 세트**: 효과를 재려면 실제 이미지로만 된 평가 세트가 있어야 한다(EXTENSION_PLAN 6.4).

## 4. 순서 (제안)

| 단계 | 내용 |
|---|---|
| **G0** | 세부 확인: 원본의 `payload-contract.md`(속성 6개의 이름과 값), 편집 모델 · VLM의 이름 · VRAM · 라이선스(가중치 · 코드 · 청사진, 상업 이용), Cosmos 3 NIM이나 사내 엔드포인트를 쓸 수 있는지, 12 GB 노드에서 Cosmos 3 Nano가 도는지 |
| **G1** | 크롭과 속성의 바탕: person 박스에서 크롭 버전 만들기, 사람 속성 태스크(속성 선언), 에디터의 속성 입력, VLM으로 원본 크롭 속성 먼저 달기 |
| **G1.5** | 최소 증강 흐름(엔드포인트 방식): 드문 속성 값을 골라 편집 → VLM 확인 → 새 버전 |
| **G2** | 노드에서 모델을 띄우는 방식, 생성기 등록과 시험 실행 · 허용 |
| **G3** | 다중 속성 분류 모델 종류와 속성별 정확도, 검수 보드, A/B 리포트 |
| 다음 | Video Data Augmentation(날씨 · 시간대 · 조명, Cosmos Transfer — 구조를 지켜 라벨을 다시 씀), 결함 이미지 생성(AnomalyGen · Qwen-Image-Edit LoRA) |

**완료 기준(G1~G3)**: person이 있는 검출 버전에서 크롭 버전을 만들고 속성을 단다 → 드문 속성 값으로 변형 300장 생성 · 확인 → 새 버전 → 검수 → 원본만과 원본 + 증강으로 학습한 사람 속성 분류 모델을, 실제 크롭으로만 된 같은 평가 세트에서 **속성별 정확도**로 비교한 수치가 나온다.

## 5. 정할 것

- ~~무엇에 쓰나~~ → **사람 속성 분류** (2026-11-19). 검출 데이터의 person 박스 크롭으로 옷 색 등 속성을 분류하는 모델을 학습한다. 사람 ID(재식별)는 필요 없다.
- **속성과 값**: 원본의 6개 그대로인가, 팀이 정하는가. 분류 모델이 배울 속성과 증강에서 바꿀 속성은 같은 목록이다.
- **모델을 어디서**: 사내 · 외부 엔드포인트가 있는가, 노드 GPU로 직접 띄우는가(필요 VRAM). 상업 이용 라이선스.
- **결과의 모양**: 크롭으로 둘지, 원래 프레임의 박스 자리에 다시 붙여 검출 학습에도 쓸지.

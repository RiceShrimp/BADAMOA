# 라벨링 계획 — 바로 고치기 · 라벨링 · 오토라벨

지금 라벨은 **가져오기로만** 들어온다(YOLO · COCO · 클래스별 폴더). 화면에서 라벨을 고치거나 그리는 기능은 없다.
이 문서는 두 가지를 계획한다.

1. **바로 고치기**: 버전(릴리스)의 이미지를 보다가 틀린 박스 · 틀린 클래스 · 빠진 라벨을 그 자리에서 고쳐 저장하고, 고친 것을 모아 새 버전으로 만든다. 작고 바로 쓸 수 있다 (3장).
2. **라벨링**: 라벨 없는 이미지를 BADAMOA 안에서 라벨링 · 오토라벨 · 검수까지 한다. 프로그램 하나에 가까운 큰 일이라 단계로 나눈다 (4장).

1의 편집 화면과 저장 방식이 2의 바탕이 된다. 그래서 1을 먼저 만든다.

**진행 상태**: 3장의 바로 고치기(3.1 · 3.2)와 배경 · 아직 안 함 구분(3.4)은 0.38.0에 구현했다. 0.39.0에 4장 3B의 일부(분할 윤곽 · 키포인트 고치기와 그리기, 분류 고치기, 휠 확대)를 앞당겨 넣었다. 3.3(잘못된 라벨 찾기)은 0.40.0에 구현했다. 4장(라벨링 묶음부터)이 남았다.

## 1. 원칙

- **라벨은 덮어쓰지 않는다.** 고친 라벨도 새 라벨 개정이다. 버전은 불변이라, 고친 라벨은 **새 버전**으로만 들어간다. 이미 학습에 쓴 버전은 그대로 남는다.
- **Hub는 얇게.** 그리기 · 편집은 브라우저에서, 무거운 모델(SAM · OVD · VLM)은 노드에서 돈다. Hub에는 torch를 넣지 않는다.
- **설치는 가볍게.** Lightly Studio는 기본 설치에 torch · DuckDB · PostgreSQL 드라이버 · pandas · OpenCV가 들어가고, FiftyOne은 MongoDB가 딸려 온다. 이런 무게를 Hub에 들이지 않는다.
- **여러 사람이 쓰는 기능이 기본.** Lightly Studio에서 Enterprise로만 열리는 여러 사용자 · 권한 · 서버 실행을 BADAMOA는 이미 갖고 있다(계정 · Hub · 노드). 배정 · 검수 · 역할도 기본 기능으로 둔다.
- **겉은 단순하게.** 데이터셋 화면에서는 "고치기" 버튼 하나로 시작한다. 라벨링 작업은 왼쪽 메뉴 Annotate에 따로 둔다.

## 3. 1단계 — 바로 고치기

**흐름**: 버전의 이미지를 넘겨 보다가 틀린 것을 발견 → 그 화면에서 고치고 저장 → 고친 라벨이 데이터셋의 **"작업 중"**에 모임 → "버전으로 확정".

git으로 치면 버전은 커밋, 작업 중은 커밋 전 변경, 확정은 커밋이다.
버전을 직접 고치면 그 버전으로 학습한 모델이 무슨 라벨로 배웠는지 알 수 없게 되고, 고칠 때마다 버전을 만들면 버전이 이미지 수만큼 생긴다.

### 3.1 화면

- **항목 보기의 "고치기"(단축키 E)**: 같은 화면이 편집 상태로 바뀐다. 고치기는 **최신 버전과 작업 중**에서만 된다. 오래된 버전에는 "최신 버전에서 고치기" 버튼을 둔다.
  - 박스: 고르기 · 옮기기 · 크기 바꾸기 · 지우기(Delete) · 새로 그리기(B, 드래그) · 복사 · 붙여넣기.
  - 클래스: 고른 박스의 클래스를 오른쪽 목록에서 고르거나 숫자키(1~9)로.
  - 배경으로: 박스를 모두 지우고 "찾을 것이 없는 이미지"로.
  - 되돌리기 · 다시 하기(Ctrl+Z · Ctrl+Shift+Z), 저장(Ctrl+S). 다음 · 이전 이미지로 넘어가면 저장하고 넘어간다. 저장하지 않고 나가려면 Esc.
  - 태스크별 범위: Det는 박스 전부, Cls는 클래스 바꾸기. Seg · Kpt는 0.38.0에는 클래스 바꾸기 · 지우기만 했고, 0.39.0에 윤곽 · 점 고치기와 그리기를 더했다.
- **"작업 중" 항목**: 데이터셋 트리에서 버전들 위에 **"작업 중 · 고친 것 12"**가 보인다.
  - 데이터셋마다 하나다. 첫 수정을 저장하면 생기고(바탕 = 그때의 최신 버전), 확정하거나 모두 되돌리면 사라진다.
  - 열면 버전 화면과 같은 화면(이미지 · 클래스 · 통계 · 비교)이다. 바탕 버전에 고친 라벨을 얹은 결과를 보여 준다. 여기서 계속 거르고 고친다.
  - 머리말: "바탕 v2 · 고친 이미지 12장 · 고친 사람 · 버전으로 확정 · 모두 되돌리기". 필터에 "고친 것만"을 두고, 그리드 썸네일에 고친 표시를 단다. 비교 탭은 바탕 버전과 비교한다.
  - 이미지 하나를 되돌리는 것은 항목 보기에서 한다.
  - 학습 · 내보내기 · 모델 평가에는 고를 수 없다. 확정되지 않은 것은 바뀔 수 있기 때문이다. 바탕 버전으로 학습을 시작하면 "작업 중에 고친 이미지 12장이 아직 버전에 없습니다"를 알려 준다.
- **버전으로 확정**:
  - 이름 · 메모를 적는 창을 연다. 메모를 비우면 "이미지 12장의 라벨을 고침"이 들어간다. split 재분배 · 클래스 바꾸기는 확정한 버전에서 "새 버전"으로 한다(0.38.0).
  - 확정한 버전의 비교 탭에는 "라벨 변경 12"로 보인다.
- **바탕보다 새 버전이 생기면**: 작업 중인 동안 다른 길(가져오기 · 버전 만들기)로 새 버전이 생기면, 작업 중의 바탕을 그 버전으로 옮길지 묻는다. 같은 이미지의 라벨이 양쪽에서 따로 바뀌었으면 그 이미지는 겹친다고 보여 주고 사람이 고른다.

### 3.2 저장 방식

- **저장할 때**: 새 라벨 개정을 하나 만든다. 출처는 `human:<사람>`이고, 고친 사람과 바탕이 된 개정을 기록한다. 내용이 기존 개정과 같으면 그 개정을 다시 쓴다.
- **작업 중 = 아직 확정하지 않은 버전**: 상태가 `draft`인 버전(릴리스)으로 둔다.
  - 처음 생길 때 바탕 버전의 이미지 목록(이미지 · split · 가리키는 개정)을 복사해 두고, 저장할 때마다 그 이미지 줄만 새 개정으로 바꾼다.
  - 그래서 그리드 · 필터 · 통계 · 비교가 지금 코드 그대로 동작한다. 학습 · 내보내기는 지금처럼 확정된(`ready`) 버전만 받는다.
  - 고친 이미지 = 바탕과 가리키는 개정이 다른 줄이다. 따로 목록을 두지 않는다.
- **확정**: 상태를 `ready`로 바꾸고 이름 · 메모 · 통계를 채운다. 다음 수정은 새 작업 중을 만든다.
- **모두 되돌리기**: 작업 중 버전을 지운다. 만든 개정은 이미지의 라벨 기록에 남는다("버전에 없는 라벨").
- **두 사람이 같은 이미지를 고치면**: 작업 중은 팀이 같이 쓴다. 저장할 때 내가 열었던 개정과 지금 작업 중의 개정이 다르면 "다른 사람이 먼저 고쳤습니다 — 그 라벨 보기 / 내 것으로 저장"을 묻는다.
- **기록과 권한**: 고친 기록은 감사 기록에 남긴다. 처음에는 로그인한 사람 모두 고칠 수 있다. 라벨러 · 검수자 역할은 4장에서 둔다.
- **MCP 도구**: 라벨 고치기와 버전으로 확정을 넣어, 에이전트도 같은 길로 라벨을 고친다.

### 3.3 잘못된 라벨 찾기 (0.40.0)

구현: 평가 코드가 `bm.log_predictions`로 이미지마다 예측과 맞춤 · 놓침 · 더 찾음을 남기고, Hub가 이미지(sha256)별로 `item_predictions`에 둔다. 버전 화면의 정렬 "라벨 의심 순"은 같은 데이터셋 · 같은 클래스 목록의 버전에서 한 평가를 고른다. 숫자는 평가할 때의 라벨 기준이다.

틀린 라벨을 사람이 넘겨 보며 찾기는 어렵다. Lightly Studio처럼 **모델의 예측과 라벨이 어긋나는 이미지부터** 보여 준다.

- **이미 있는 것**: 평가 작업이 이미지마다 맞춘 것 · 놓친 것 · 더 찾은 것을 기록한다(`templates/yolo/ops.py`의 `per_image`).
- **더할 것**:
  - 평가가 이미지별 예측 박스도 남긴다. 예측은 따로 저장해 버전에 섞이지 않게 한다.
  - 버전 화면 그리드에 "라벨 의심 순" 정렬을 둔다. 고른 모델의 평가에서 놓침과 더 찾음이 많은 이미지가 앞에 온다.
  - 항목 보기에서 예측을 점선으로 겹쳐 본다. 예측 박스를 눌러 "라벨로 넣기"를 하면 빠진 라벨이 바로 채워진다.
- 학습한 모델이 라벨 오류를 찾아 주고, 사람은 고치기만 하는 고리가 생긴다. 고친 것을 확정한 버전으로 다시 학습하면 그 효과도 비교 탭에서 바로 확인한다.

### 3.4 배경과 아직 라벨 안 함

0.34.0부터 라벨이 없는 이미지는 모두 배경으로 등록한다(YOLO 관례). 그래서 지금은 "아직 아무도 안 본 이미지"를 나타낼 수 없다.
구분할 기준은 이미 데이터에 있다. 라벨 개정마다 **빠짐없이 본 클래스** 목록이 있고, 지금 배경으로 들어온 이미지는 이 목록에 모든 클래스가 들어가 있다.

| 상태 | 박스 | 빠짐없이 본 클래스 | 뜻 |
|---|---|---|---|
| 라벨 있음 | 있음 | 전부 | 다 봤고, 있는 것은 다 그렸다 |
| 배경 | 없음 | 전부 | 다 봤는데 찾을 것이 없다 |
| **아직 안 함** | 없음 | 없음 | 아무도 보지 않았다 |
| (일부만 봄) | 있음 · 없음 | 일부 | 클래스를 나중에 늘린 경우. 지금도 처리한다 |

- **상태 값**: `unlabelled`("아직 안 함")를 다시 둔다. 빠짐없이 본 클래스는 비운다.
- **가져올 때 기본값**: 라벨 파일이 하나도 없는 폴더(이미지만 있음)는 "아직 안 함"으로, 라벨이 있는 데이터셋에서 일부만 없는 이미지는 지금처럼 배경으로 받는다. 가져오기 창에서 바꿀 수 있다.
- **바뀌는 때**: 열어 보기만 해서는 바뀌지 않는다. 박스를 그려 저장하면 "라벨 있음"이 된다. "배경" 버튼을 누르거나 박스를 다 지우고 저장하면 "배경"이 된다. 사람이 보고 확인한 것이기 때문이다.
- **학습**: "아직 안 함"은 학습에서 뺀다. 배경으로 넣으면 "물체 없음"으로 잘못 배운다. 학습을 시작할 때 "라벨 안 한 이미지 N장은 뺍니다"라고 알려 준다.
- **화면**: 그리드 배지, 라벨 상태 필터, 통계 타일에 "아직 안 함"을 넣는다.

## 4. 2단계 이후 — 라벨링 (Phase 3를 "라벨링 · 오토라벨"로 넓힘)

**프로그램을 따로 두지 않고**, 같은 Hub 안에 Annotate라는 자기 영역(왼쪽 메뉴, `hub/annotate/`, `web/src/annotate/`)으로 만든다.
같은 이미지 · 라벨 개정 · 계정 · 노드를 쓰기 때문이다. 따로 두면 둘 사이를 맞추는 일이 생기고, 설치가 둘이 된다.

| 단계 | 내용 | 바탕 |
|---|---|---|
| **3A 라벨링 묶음** | 버전 · 필터 · 태그 · 가져오기 배치에서 이미지를 골라 **라벨링 묶음**을 만든다(클래스 · 태스크 · 지시문). N장씩 나눠 사람에게 배정한다. 보드는 미배정 → 오토라벨 → 라벨링 → 검수 → 완료이고, 완료된 라벨은 3장과 같은 길로 데이터셋의 작업 중에 모였다가 확정된다. 라벨링할 이미지는 "아직 안 함"(3.4)으로 고른다 | CVAT 일감 배정, Roboflow 보드 |
| **3B 에디터** | 도형을 차례로 늘린다: 박스 → 폴리곤 → 점 · 스켈레톤(라벨 공간의 점 이름 · 연결선) → 브러시 마스크 → 이미지 분류(여러 라벨) → 속성(가림 · 잘림 · 난이도). 확대 · 이동, 단축키, 직전 이미지 라벨 복사, 박스 단위 그리드와 일괄 클래스 변경, 예측 깔아 두기 · 수락 | CVAT 도구 · 단축키, Lightly 박스 그리드, Label Studio 예측 |
| **3C 스마트 도구** | SAM 클릭 → 마스크 · 박스. 이미지 임베딩은 노드가 계산하고, 브라우저가 작은 디코더(ONNX Runtime Web)를 돌려 클릭마다 바로 반응하게 한다. Hub는 그대로 가볍다. 영상 · 시퀀스 트랙 보간은 시퀀스 항목이 생긴 뒤에 | CVAT AI 도구 |
| **3D 오토라벨** | (기존 Phase 3 계획) Labeler 플러그인(OVD → SAM → VLM 재확인 → SigLIP2 분류)과 등록한 모델로 예측, 신뢰도 라우팅(자동 승인 · 검수 · 폐기), 오토라벨 정밀도 리포트. 지금 걸러 낸 보기 전체에 돌릴 수 있고, 돌릴 노드는 0.37.0의 노드 고르기를 그대로 쓴다 | Lightly 플러그인 실행, ARCHITECTURE Annotate |
| **3E 검수 · 협업** | 검수(승인 · 거절 · 이미지 위 이슈), 겹쳐 라벨링과 작업자 간 일치도, 작업자별 진행 · 속도, 역할(라벨러 · 검수자 · 관리자) | CVAT 이슈, Label Studio 일치도 |
| **3F 큐레이션 연결** | Phase 2의 임베딩이 생긴 뒤: 임베딩 지도와 올가미 선택, 비슷한 이미지 · 텍스트 검색, 다양성 · 대표성 샘플링 → 태그 → 라벨링 묶음 | Lightly 지도 · 샘플링 |
| **3G 외부 도구** | CVAT · Label Studio 내보내기 · 가져오기. 이미 그 도구를 쓰는 팀을 위해 유지한다 | — |

**완료 기준**(기존 Phase 3 기준을 넓힘): 라벨 없는 1천 장 → 오토라벨 → 두 사람이 나눠 라벨링 · 검수 → 새 버전 → 학습. 정답 셋 대비 오토라벨 mAP와 작업자 간 일치도를 잰다.

## 5. 데이터 모델에 더할 것

| 무엇 | 내용 | 단계 |
|---|---|---|
| `label_revisions` 열 | 바탕 개정(`parent_id`), 만든 사람(`created_by`) | 1 |
| 버전 상태 `draft` | 작업 중. 데이터셋마다 하나, 바탕 버전의 이미지 목록을 복사해 두고 고친 이미지 줄만 바꾼다 | 1 |
| 라벨 상태 `unlabelled` | "아직 안 함". 빠짐없이 본 클래스가 비어 있다 (3.4) | 1 |
| 예측 | 모델 버전 · 이미지 · 박스(점수 포함). 라벨 개정과 따로 두어 버전에 섞이지 않게 | 3.3 |
| 라벨링 묶음 | 묶음(이름 · 클래스 · 태스크 · 지시문 · 상태), 묶음의 이미지(배정된 사람 · 상태 · 개정), 이슈 | 3A · 3E |
| 박스 속성 | 박스 목록 옆에 속성 목록을 나란히 둔다. 지금 형식 `[클래스, cx, cy, w, h, …]`은 바꾸지 않는다 | 3B |

# 템플릿 확인 계획 — 돌아가는 것만 쓸 수 있게

지금은 모델 템플릿을 올리면 선언 파일(`badamoa.toml`)만 검사하고 바로 학습 대화상자에 나온다.
코드가 실제로 도는지는 누군가 학습을 시작하고, GPU를 잡고, 실패해야 안다.
고른 데이터 버전과 템플릿이 맞지 않을 때도 대부분 노드에서 처음 드러난다.

이 문서는 세 가지를 계획한다.

1. 올린 템플릿은 **노드에서 짧게 돌려 보고 통과해야** "쓸 수 있음"이 된다 (5장).
2. 템플릿이 받는 데이터를 선언하고, **학습을 시작하기 전에** 고른 버전과 맞는지 검사한다. 맞지 않으면 시작하지 않고 이유를 보여 준다 (4장).
3. 팀이 이름 붙인 태스크와 사내 학습 코드도 **같은 틀**에 넣는다 (6장).

**진행 상태**: 계획. 정할 것은 11장.
설계 배경은 [EXECUTION_PLAN.md](EXECUTION_PLAN.md) 2장(템플릿 형식) · 3장(환경).

## 0. 지금 검사하는 것

| 시점 | 검사함 | 검사하지 않음 |
|---|---|---|
| 올릴 때 (Hub, `core/templates.py`) | zip 경로 안전 · 64 MB, 선언 형식, name · version, 태스크 이름, `data_format`이 yolo · yolo-seg · imagefolder 중 하나, train 진입점과 `{config}`, 설정의 이름 · 종류 · 기본값, train 스크립트의 `bm.params` 문법 | 진입점이 가리키는 .py가 묶음에 있는지, 다른 .py의 문법, 태스크와 형식의 짝, 패키지가 설치되는지, 코드가 끝까지 도는지, 가중치를 남기는지, eval · predict · export가 도는지 |
| 학습 시작 (Hub, `training.start_run`) | 템플릿 태스크 = 데이터셋 태스크, 설정 값, 클래스 id | 노드가 그 형식으로 풀 수 있는지, 학습할 이미지 · 클래스 수가 충분한지 |
| 학습 중 (노드, `node/trainer.py`) | 형식 변환기가 있는지, 종료 코드, `result` 이벤트, 가중치 파일 | — 여기서 실패하면 이미 GPU를 잡고 데이터를 푼 뒤다 |

읽으면서 찾은 빈틈:

- **팀 태스크의 라벨 값이 그대로 남지 않는다.** YOLO 라벨을 읽을 때 값 개수로 윤곽인지 추측한다(`node/importer.py`의 `_read_yolo_label`).
  `0 cx cy w h a b`는 윤곽으로 읽혀 박스가 바뀌고, `0 cx cy w h a`는 `a`가 버려진다. 값을 0~1로 자르기도 한다.
- **팀 태스크를 풀어 줄 형식이 없다.** `yolo`는 박스만 쓰고, `yolo-seg`는 박스 뒤의 값을 윤곽으로 쓴다.
- **Kpt는 학습 형식이 없다.** 태스크가 `pose`인 템플릿은 등록되지만 학습이 노드에서 실패한다.
- **팀 태스크에는 대표 지표가 없다** (`training.PRIMARY_METRIC`). 모델 순위와 "가장 좋은 step"의 기준이 없다.

## 1. 원칙

1. **"쓸 수 있음"은 실제로 돌려 본 것만.** 선언이 맞는 것과 코드가 도는 것은 다르다.
2. **실패는 GPU를 잡기 전에, 할 수 있는 일과 함께** (EXECUTION_PLAN 1.1의 5).
3. **겉은 단순하게.** 일반 사용자는 쓸 수 있는 템플릿만 본다. 상태 · 단계 · 로그는 관리자 설정에 둔다.
4. **확인은 가볍게.** CPU 서버 한 대, 이미지 열두 장, 1 epoch. 같은 코드 · 같은 환경은 다시 돌리지 않는다.
5. **새 라이브러리 없이.** 지금 있는 작업(job) · 형식 변환기 · SDK를 넓힌다. 합성 이미지는 이미 쓰는 Pillow로 만든다.

## 4. 데이터 맞춤 — 템플릿이 받는 데이터를 선언한다

### 4.1 선언

지금 있는 `task` · `data_format`에 조건 몇 개를 더한다. 적지 않으면 태스크의 기본값이다.

```toml
task = "classify"
data_format = "imagefolder"

[data]
classes = { min = 2 }      # 클래스 수 범위. 분류는 기본 min = 2, 그 밖은 1. max는 적지 않으면 제한 없음
min_images = 8             # 학습에 들어갈 라벨 있는 이미지의 최소 (기본 1)
keypoints = 17             # Kpt: 점 개수가 정해진 모델이면. 0이면 아무 개수

[metrics]                  # 팀 태스크에 필요
primary = "cer"            # 모델 순위 · 가장 좋은 step의 기준
goal = "min"               # 작을수록 좋음 (기본 max)
```

- 기본 태스크의 대표 지표는 지금 정해진 것(map50_95 · mask_map50_95 · top1)을 그대로 쓴다. 템플릿끼리 비교가 되어야 하기 때문이다.
- 팀 태스크는 템플릿이 적는다. 같은 태스크를 먼저 등록한 템플릿과 다르게 적으면 등록 때 알린다. 순위는 대표 지표가 같은 모델끼리 매긴다.

### 4.2 시작 전 검사

Hub가 버전의 통계(클래스별 라벨 수 · split별 이미지 수 · 라벨 상태)로 계산한다. 노드에 묻지 않는다.

| 검사 | 결과 | 메시지 예 (할 일과 함께) |
|---|---|---|
| 태스크가 다름 | 막음 (지금 있음) | 이 모델은 Det용이고 이 데이터셋은 Cls입니다 |
| 템플릿이 시험 실행을 통과하지 않음 | 막음 | 이 모델 종류는 아직 확인되지 않았습니다. 관리자에게 문의하세요 |
| 학습할 서버의 BADAMOA가 그 형식을 모름 | 막음 | ○○ 서버의 BADAMOA가 오래되었습니다. 서버를 업데이트하세요 |
| 고른 클래스 수가 `[data] classes` 범위 밖 | 막음 | 이 모델은 클래스가 2개 이상이어야 합니다. 클래스를 더 고르세요 |
| 고른 클래스로 학습에 들어갈 라벨 있는 이미지 < `min_images` | 막음 | 학습에 쓸 라벨 있는 이미지가 3장입니다 (8장 필요) |
| Kpt 점 개수가 `keypoints`와 다름 | 막음 | 이 모델은 점 17개를 받습니다. 이 데이터셋은 5개입니다 |
| val split이 없음 | 알림 | val이 없어 train의 20%를 검증에 씁니다 |
| 분류: train에 이미지가 없는 클래스 | 알림 | `dog` 클래스는 train에 이미지가 없습니다 |
| 고른 클래스가 다 라벨되지 않은 이미지가 빠짐 | 알림 | 고른 클래스가 모두 라벨되지 않은 이미지 120장은 빠집니다 |
| 시험 실행한 환경과 다른 환경을 고름 | 알림 | 이 환경으로는 시험 실행하지 않았습니다 |

- 대화상자는 버전 · 모델을 고를 때마다 검사한다. 막히면 **시작 버튼 아래 한 줄**로 이유를 보여 주고 버튼을 끈다. 알림은 작은 글씨로 둔다.
- `start_run`도 같은 검사를 한다 (API · MCP · 탐색 · 다시 실행 모두). 대화상자용으로 시작하지 않고 검사만 하는 API를 둔다.
- 평가(`model.run`의 eval)도 같은 검사를 한다: 태스크, 형식, 고른 split에 이미지가 있는지.
- 서버가 풀 수 있는 형식은 노드가 정보에 실어 보낸다 (`formats`).

### 4.3 태스크와 형식의 짝

템플릿은 자기 태스크의 데이터만 받으므로(지금도 그렇다) 짝은 템플릿 하나 안에서 정해진다. 등록할 때 이 표로 검사한다.

| 태스크 \ 형식 | yolo | yolo-seg | yolo-pose | imagefolder | coco | manifest |
|---|---|---|---|---|---|---|
| Det | ✅ | — | — | — | 계획 | 계획 |
| Seg | ⚠ 박스만 | ✅ | — | — | 계획 | 계획 |
| Kpt | ⚠ 박스만 | — | 계획 (pose 템플릿과) | — | 계획 | 계획 |
| Cls | — | — | — | ✅ | — | 계획 |
| 팀 태스크 | ⚠ 박스만 | — | — | — | — | 계획 — 값을 그대로 넘기는 유일한 형식 |

- ✅ 됨 · ⚠ 되지만 값 일부가 버려짐(등록 때 알림) · — 등록 거부 · 계획: 그 형식이 생기면 됨.
- **변환기가 없는 짝은 등록하지 않는다.** 등록해 두고 학습 때 실패하는 것보다 낫다. 메시지에 쓸 수 있는 형식을 함께 적는다.
- 내려받기용 COCO 쓰기(`exporter.write_archive`)는 이미 있다. 학습 형식의 COCO는 그것을 다시 쓴다.

### 4.4 manifest 형식 — 모든 태스크의 출구

자체 데이터 로더가 있는 코드용이다 (EXECUTION_PLAN 2.2에서 이름만 정해 둔 것).
이미지는 지금처럼 링크로 두고, 라벨은 **저장된 값 그대로** 한 줄에 한 이미지로 적는다.

```
data/
  dataset.json        {"schema": 1, "task": "OCR", "classes": ["plate", "char"], "splits": {"train": 96, "val": 24}}
  manifest.jsonl      이미지 한 장에 한 줄
  images/<split>/…    지금처럼 원본을 가리키는 링크
```

```json
{"image": "images/train/3f9a….jpg", "split": "train", "width": 1920, "height": 1080,
 "name": "cam1/0001.jpg", "labels": [[0, 0.51, 0.62, 0.20, 0.08, 0.13, 0.77]]}
```

- `labels`의 행은 카탈로그에 저장된 `[클래스, cx, cy, w, h, …]` 그대로다. 클래스 번호만 학습 순서(0부터)로 바꾼다.
- 라벨 속성(LABELING_PLAN 3B)이 생기면 같은 줄에 `attributes`로 붙는다.
- config의 `data`는 `manifest.jsonl`의 경로다. SDK에 읽기 도우미를 둔다: `for row in bm.rows("train"): …`.
- `schema` 번호는 이 형식을 바꿀 때만 올린다. 코드는 모르는 번호를 보면 멈춘다.

## 5. 시험 실행

### 5.1 흐름

```
올림 → ① 정적 검사 → 상태 "확인 중" → 작업 template.check (GPU 0장)
     → 노드: 환경 준비 → 시험 데이터를 템플릿 형식으로 → train → eval → predict → export
     → Hub: 단계별 결과 → "쓸 수 있음" 또는 "실패: 이유"
```

1. 정적 검사를 통과하면 템플릿 버전은 **확인 중**이 되고 `template.check` 작업이 하나 생긴다. GPU를 잡지 않는다 (5.4의 `gpu = true`일 때만 1장).
2. 노드가 환경을 준비한다. 자동 설치면 이때 설치되고, 그 서버의 첫 학습은 다시 설치하지 않는다 (`env.prepare`와 같은 경로).
3. 시험 데이터(5.3)를 템플릿의 형식으로 푼다. 학습 때와 같은 변환기다.
4. train 진입점을 짧은 설정(5.4)으로 실행한다.
5. 선언한 진입점만 이어서: 남긴 가중치로 eval(val) → predict(2장) → export(첫 형식).
6. 단계별 결과 · 걸린 시간 · 실패한 단계의 마지막 로그 · 패키지 목록을 Hub에 보낸다.

등록은 관리자만 하므로, 올리자마자 코드를 실행하는 것은 지금 학습을 시작하는 것과 같은 신뢰 수준이다 (EXECUTION_PLAN 6장).

### 5.2 통과 기준

| 단계 | 통과 | 실패 메시지 예 |
|---|---|---|
| 환경 | 설치 성공, 또는 등록된 Python이 실행됨 | 패키지 설치 실패: `torch==9.9`를 찾을 수 없습니다 |
| 학습 | 종료 코드 0, `result` 이벤트, 알린 가중치 파일이 있고 비어 있지 않음, 지표 1개 이상 | 학습 코드가 끝날 때 `bm.finish`를 부르지 않았습니다 |
| 평가 | `result`에 지표 1개 이상 | 평가 코드가 종료 코드 1로 끝났습니다 (로그 보기) |
| 테스트 | 넘긴 이미지마다 `predictions` 한 항목 | 2장을 넘겼는데 예측이 0개입니다 |
| 내보내기 | 파일 1개 이상 기록 | 내보낸 파일이 없습니다 |
| 시간 | 정한 시간 안 (기본 15분, 환경 설치는 빼고) | 15분 안에 끝나지 않았습니다. `[check] params`로 더 짧게 하세요 |

통과는 하지만 알리는 것:

- 대표 지표(Det `map50_95` · Seg `mask_map50_95` · Cls `top1` · 팀 태스크 `[metrics] primary`)를 보고하지 않음 → 모델 순위에 나오지 않는다.
- `resume = true`인데 체크포인트를 한 번도 알리지 않음 → "이어서 실행"이 안 된다.
- 평가가 클래스별 지표를 주지 않음.

지표 값이 그럴듯한지는 보지 않는다. 열두 장으로 1 epoch 학습한 지표는 의미가 없다.

### 5.3 시험 데이터

| 출처 | 언제 | 내용 |
|---|---|---|
| 내장 합성 샘플 | Det · Seg · Kpt · Cls의 기본 | 노드가 그 자리에서 만든다. 색 사각형과 그 박스 · 윤곽 · 점, 분류는 클래스마다 다른 색. train 8 · val 4장, 160 px, 클래스 2개. 내려받는 것이 없어 폐쇄망에서도 된다. 테스트용 `tests/sample_data.py`를 패키지 안으로 옮겨 쓴다 |
| 템플릿이 함께 올린 샘플 | **팀 태스크는 필수**, 기본 태스크는 있으면 이것을 먼저 | 묶음 안 `check/` 폴더. BADAMOA가 가져올 수 있는 형식(YOLO · COCO · 클래스별 폴더), 5 MB 이하. 카탈로그에 등록하지 않고 노드가 가져오기 코드로 읽어 바로 변환한다 |
| 고른 데이터 버전의 일부 | 관리자가 "이 데이터로 확인"을 누를 때 | 그 버전에서 정해진 순서로 train 16 · val 8장. 그 이미지가 있는 서버에서 돈다. 실제 해상도 · 라벨 모양으로 확인하고 싶을 때 |

### 5.4 짧게 돌리기

템플릿이 시험 실행 때 쓸 값을 적는다.

```toml
[check]
params = { epochs = 1, imgsz = 64, model = "yolo11n.pt" }   # 시험 실행에서만 쓰는 설정 값
timeout_min = 15        # 환경 설치를 뺀 시간. 관리자 설정의 상한을 넘지 못함
gpu = false             # CPU로 돌 수 없는 코드(CUDA 전용 연산)만 true: GPU 1장을 짧게 잡는다
skip = []               # 시험하지 않을 진입점. 예: ["export"] (GPU 서버에서만 되는 내보내기)
```

- `[check]`를 적지 않으면 설정은 기본값이고, `epochs`라는 설정이 있으면 1로 둔다.
- config에 `"check": true`가 들어간다. SDK의 `run.check`로 읽어 몇 step 만에 멈출 수 있다: `if run.check and step >= 3: break`.
- 내장 템플릿도 같은 칸을 적는다: YOLO는 `yolo11n.pt` · imgsz 64, torchvision 검출은 SSDlite, 분류는 ResNet-18 · 64 px.
- 사전학습 가중치를 받는 템플릿은 시험 실행 때 받아 캐시에 둔다. 인터넷이 없는 서버면 여기서 실패로 드러난다 — 실제 학습에서도 실패할 일이다.
- 시험 실행은 GPU 학습이 도는 서버에서도 돌 수 있으므로 CPU 스레드를 4개로 제한한다 (`OMP_NUM_THREADS` 등).

### 5.5 상태

템플릿 **버전마다** 상태가 하나다.

| 상태 | 뜻 | 학습 대화상자 (일반 사용자) | 관리자 설정 → 모델 종류 |
|---|---|---|---|
| 확인 중 | 시험 실행 대기 · 진행 | 안 보임 | 지금 단계 |
| 쓸 수 있음 | 통과 | 보임 | 마지막 확인: 날짜 · 서버 · 환경 · 걸린 시간 |
| 실패 | 한 단계가 실패 | 안 보임 | 실패한 단계, 한 문장 이유, 로그 |
| 확인 못 함 | 돌릴 서버가 없음 (모두 꺼짐, GPU 서버 없음 …) | 안 보임 | 이유와 "다시 확인" |
| 허용 | 관리자가 이유를 적고 확인 없이 허용 | 보임 | 누가 · 언제 · 이유 (감사 로그) |

- 내장 템플릿은 BADAMOA를 내기 전에 확인하므로 처음부터 **쓸 수 있음**이다. 서버의 환경이 맞는지 보고 싶으면 관리자가 "이 서버에서 확인"을 누른다.
- 새 버전이 확인 중이거나 실패하면, 학습 대화상자는 **그 템플릿의 마지막으로 통과한 버전**을 쓴다. 새 버전을 올리다 실패해도 쓰던 모델 종류가 사라지지 않는다.

### 5.6 다시 확인할 때

| 일 | 동작 |
|---|---|
| 새 버전을 올림 | 그 버전만 확인. 앞 버전은 그대로 |
| 같은 내용(같은 해시)을 다시 올림 | 앞 결과를 그대로 |
| 기본 환경이 바뀜 (등록된 환경의 경로, 앞으로 Docker 이미지 다이제스트) | 그 환경을 쓰는 템플릿을 뒤에서 다시 확인. 결과가 나올 때까지 지금 상태 유지 |
| BADAMOA가 템플릿과의 약속(config · 형식 · SDK)을 바꿈 | 약속 번호가 올라가면 모든 템플릿을 뒤에서 다시 확인, 같은 방식 |
| 관리자가 "다시 확인" | 바로 |
| 실제 학습이 성공 | "확인 못 함"이나 "허용"이던 버전은 "쓸 수 있음"으로. 실제로 돈 것이 증거다 |
| 실제 학습이 실패 | 상태를 바꾸지 않는다. 데이터나 설정 탓일 수 있다 |

약속 번호는 `core/templates.py`의 상수 하나다 (`CONTRACT = 1`). 지금처럼 하위 호환을 지키면 올릴 일이 거의 없다.

### 5.7 환경마다 다른 것

| 환경 | 시험 실행 | 주의 |
|---|---|---|
| 자동 설치 | `env.prepare`와 같은 설치. 그 서버의 학습이 그 환경을 그대로 씀 | 서버마다 OS · 드라이버가 달라 PyTorch 빌드가 다르다. 확인은 한 서버에서만 하고, 다른 서버는 첫 학습 때 설치한다(실패하면 서버 이름과 함께). 관리자는 "모든 서버에서 확인"을 누를 수 있다 |
| 서버의 기존 Python | 경로가 적힌 서버 하나에서 그 Python으로. 패키지를 설치하지 않으므로 import 실패를 여기서 잡는다 | 서버마다 경로 · 내용이 다를 수 있다. 결과를 서버별로 남긴다 |
| Docker (EXECUTION_PLAN 7장 5단계 뒤) | 이미지를 받아 컨테이너에서 같은 절차, 다이제스트 기록 | Linux 서버만. 다이제스트가 바뀌면 다시 확인 |

시험 실행할 서버를 고르는 순서: 기본 환경이 이미 준비된 서버 → (데이터 버전으로 확인할 때) 그 이미지가 있는 서버 → 켜진 아무 서버.
`gpu = true`가 아니면 GPU가 비었는지는 보지 않는다.

## 6. 팀 태스크와 사내 코드의 약속

사내 코드는 지금의 약속(EXECUTION_PLAN 2.3, `badamoa_sdk`)을 그대로 지키고, 아래만 더한다.

| 무엇 | 약속 | 어디에 |
|---|---|---|
| 태스크 | 기본 태스크(Det · Seg · Kpt · Cls) 또는 팀 태스크 이름 그대로 (예: `OCR`) | `badamoa.toml`의 `task` |
| 받는 데이터 | 형식(4.3의 표 안에서), 클래스 수 · 이미지 수 · 점 개수 조건 | `data_format`, `[data]` |
| 대표 지표 | 팀 태스크는 필수 | `[metrics]` |
| 시험 실행 | 짧게 돌리는 값, 팀 태스크는 샘플 | `[check]`, `check/` 폴더 |
| 입력 | config JSON 그대로 + `check`. manifest면 `data`가 `manifest.jsonl` | 4.4 |
| 출력 | SDK 그대로. 학습은 `bm.log_model` + `bm.finish`가 있어야 통과 | `badamoa_sdk` |

팀 태스크의 라벨 값:

- 지금 저장 형식 `[클래스, cx, cy, w, h, …값]`을 그대로 쓴다. 가져오기에서 팀 태스크는 값 개수로 윤곽을 추측하지 않고, 박스 뒤의 값을 자르지도 바꾸지도 않는다 (0장의 빈틈을 고친다).
- 숫자가 아닌 라벨(OCR 글자, 이미지 하나에 값 하나)은 라벨 속성(LABELING_PLAN 3B)이 생기면 manifest의 `attributes`로 함께 넘긴다.
- 원본 라벨 파일을 그대로 넘기는 방식은 하지 않는다. 버전이 라벨을 고정한다는 약속이 깨진다.

만드는 사람의 흐름:

```bash
badamoa template init my-ocr --task OCR      # data_format = "manifest", [metrics] · [check] 칸, check/ 자리
badamoa template check my-ocr --run          # 올리기 전에 내 PC에서 같은 시험 실행 (5장)
badamoa template push my-ocr --wait          # 올리고 Hub의 시험 실행 결과까지 기다려 출력
```

`--run`은 노드의 시험 실행 코드를 그대로 쓴다. 고치고 올리고 실패를 기다리는 일을 내 PC에서 끝낸다.

## 8. 데이터 모델

| 표 | 더할 것 |
|---|---|
| `templates` | `status`(checking · ready · failed · unchecked · allowed), `check`(JSON: 단계별 결과 · 서버 · 환경 식별 · 약속 번호 · 걸린 시간 · 작업 id · 확인 시각), `allowed_by` · `allowed_reason` |
| `jobs` | 새 종류 `template.check`. 로그와 결과는 다른 작업처럼 남는다 |
| 노드 정보 | 이 BADAMOA가 풀 수 있는 형식 목록 (`formats`) |

이력은 작업 목록에 남으므로 따로 표를 두지 않는다. 템플릿에는 마지막 결과만 둔다.
이미 등록된 사내 템플릿을 어떻게 옮길지는 11장 Q5.

## 9. 구현 순서

각 단계는 그것만으로 쓸 수 있게 끝낸다. 확인은 가볍게 한다 (합성 샘플, COCO128, 가장 작은 YOLO).

| 단계 | 내용 | 확인 방법 | 이 PC에서 확인 |
|---|---|---|---|
| **1** 정적 검사와 시작 전 검사 | 3장, `[data]` · `[metrics]`, 4.3의 표, 학습 · 평가 시작 전 검사와 대화상자 안내, 검사만 하는 API, 노드의 `formats` | 잘못된 묶음(진입점 파일 없음 · 문법 오류 · 없는 짝)을 거부, 클래스 1개짜리 분류 버전으로 시작 거부 | 가능 |
| **2** 시험 실행 | `template.check` 작업, 합성 샘플(Det · Seg · Cls), `[check]`, 상태와 대화상자 거르기(마지막 통과 버전), 관리자 화면, `push --wait` · `check --run` | `dummy`로 통과 · `fail = true`로 실패 · `finish`를 빼서 실패, YOLO11n을 CPU로 시험 실행 | 가능 |
| **3** 팀 태스크 | manifest 형식, 팀 태스크 가져오기의 값 보존, `check/` 샘플, `[metrics]`로 순위, SDK `bm.rows` | 값 하나를 회귀하는 작은 팀 태스크 템플릿: 가져오기 → 시험 실행 → 학습 → 모델 순위 | 가능 |
| **4** 다시 확인과 실데이터 확인 | 데이터 버전으로 확인, 환경 · 약속 번호가 바뀌면 다시 확인, 실제 학습 성공으로 "쓸 수 있음", 모든 서버에서 확인 | 등록된 환경의 경로를 바꿔 다시 확인되는지, COCO128 버전으로 확인 | 가능 |
| **5** Docker | EXECUTION_PLAN 5단계와 함께 | Linux GPU 서버 | 불가 |

Kpt 학습 형식(`yolo-pose`)과 합성 Kpt 샘플은 YOLO pose 템플릿(ROADMAP의 키포인트 항목)과 함께 넣는다.

순서의 이유: 1은 노드 없이 Hub만 고치고, 지금 노드에서 늦게 드러나는 실패 대부분을 앞으로 당긴다. 2가 "쓸 수 있음"의 본체다. 3은 2의 틀(시험 데이터, 형식 표) 위에 얹는다.

## 10. 만들지 않는 것

- 지표가 그럴듯한지 보는 확인. 시험 실행은 "끝까지 돌고 약속대로 결과를 남긴다"만 본다.
- 모든 서버 × 모든 환경 자동 확인. 한 서버에서 하고, 나머지는 관리자가 요청할 때.
- 코드 보안 검사. 등록은 관리자만 한다는 지금의 경계를 그대로 둔다.
- 템플릿 마켓 · 공유 (EXECUTION_PLAN 8장 그대로).

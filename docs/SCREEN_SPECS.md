# 화면 설계 — 데이터셋 · 노드 자원

사내에서 이미 쓰고 있는 두 화면(Dataset Catalog, 서버 모니터)의 캡처와 Ultralytics Platform의 데이터셋·프로젝트 화면을 바탕으로,
BADAMOA의 데이터셋 화면과 노드 자원 화면이 **무엇을 보여 주고 어떤 데이터가 필요한지** 정리한 문서입니다.
두 플랫폼 비교는 [REFERENCE_STUDY.md](REFERENCE_STUDY.md), 전체 구조는 [ARCHITECTURE.md](ARCHITECTURE.md).

**두 사내 도구는 참고 대상입니다.** BADAMOA는 이들을 대체하거나 데이터를 옮겨 오지 않고, 실제 업무에서 다듬어진 개념과 화면 구성을 배워 자체 화면을 만듭니다. 두 도구는 계속 따로 운영됩니다.

## 1. 사내 화면에서 읽은 것

### 1.1 Dataset Catalog

| 화면 요소 | 내용 | 뜻하는 것 |
|---|---|---|
| 왼쪽 트리 | 데이터셋 계열(이름) → 릴리스 목록, 계열마다 릴리스 개수, 이름 검색 · 태스크 필터 · 모두 펼치기/접기 | 데이터셋은 **계열 + 릴리스**의 2단 |
| 최상위 메뉴 | All images / All sequences | 항목은 이미지와 **시퀀스** 두 종류 |
| 릴리스 머리말 | 이름 + 버전, 라벨 공간(od11), 릴리스 날짜, **base 릴리스** | 릴리스는 이전 릴리스에서 파생된다 |
| 통계 타일 | 전체 항목 수와 용량, train / val 수와 용량, 라벨 있음, **배경(라벨 없음)** | 라벨 상태는 두 가지: 라벨 있음 / 배경 (0.34.0) |
| 접이식 | 클래스별 박스 수(총 540만), Import note | |
| Compare | 다른 릴리스 선택 또는 base와 비교 | 릴리스 간 차이 보기가 일상 작업 |
| 필터 | split · 라벨 상태 · 클래스 · 사이트 · 카메라 · 파일 이름 | 사이트와 카메라가 1급 메타데이터 |
| 그리드 | 썸네일, 파일 이름, split, 박스 수 또는 background, 해상도 · 페이지 이동(9,517쪽) | 57만 장을 서버 쪽 페이지로 |
| 기타 | Export, API 문서(openapi) | |

이미지 상세:

| 화면 요소 | 내용 | 뜻하는 것 |
|---|---|---|
| 오버레이 | 라벨 · 클래스 이름 · 박스 채우기 · **이 릴리스의 클래스만** — 각각 단축키 | 한 손으로 넘겨 보며 확인 |
| 클래스 칩 | 클래스별 개수, All / None | 클래스별 표시 전환 |
| **Label revisions** | 이미지마다 라벨 개정 여러 개: 번호 · 박스 수 · 라벨 공간 · 날짜 · 출처(어느 import) · "this release" 표시 | 라벨은 덮어쓰지 않고 **개정으로 쌓인다**. 릴리스는 이미지마다 특정 개정을 가리킨다 |
| 라벨 공간 상세 | od15 · 15 classes, **"labelled here"** 클래스 목록 | 그 개정에서 **빠짐없이 라벨한 클래스**가 무엇인지 기록 — 없는 박스가 "없음"인지 "안 봄"인지 구분 |

| **Releases (28)** | 이 이미지가 들어간 모든 릴리스와 그때의 split · 개정 | 이미지 → 릴리스 역참조 |
| 이동 | 60 / 570,978 | 릴리스 안에서 순서대로 넘기기 |

규모: 한 릴리스에 57만 장 · 301 GB · 박스 540만 개, 한 이미지가 28개 릴리스에 공유, 계열 20여 개.
데이터 종류: 객체 탐지(OD_*) 외에 **스켈레톤·동작·모션 데이터셋**(NTU, AMASS, BABEL, Inter-X 등)이 있음.

### 1.3 Ultralytics에서 추가로 본 것

- 데이터셋에서 이미지를 누르면 **보기와 편집이 한 화면**: 그리기 · 스마트 도구, 단축키 안내, 확대, 오른쪽 클래스 목록(개수 · 숫자 단축키 · 검색 · 클래스 추가), 아래 막대(순번 · 파일 이름 · 크기 · split · 어노테이션 수 · 클래스 칩).
- 프로젝트: 왼쪽 모델 목록에서 고른 모델들의 지표를 오른쪽 **작은 그래프 여러 개**로 겹쳐 봄(precision · recall · mAP · 크기별 mAP, Loss, Learning rate 묶음, 묶음별 표시 개수 설정).

## 2. BADAMOA 데이터 모델에 반영

사내 Catalog의 개념을 그대로 받아들입니다. 용어도 사내에서 쓰는 **릴리스**로 통일합니다(앞선 문서의 DatasetVersion과 같은 것).

```
Project
 ├─ 라벨 공간 (Label space)          클래스 집합의 버전. 예: od11, od15, od18
 ├─ 샘플 라이브러리                    항목 = 이미지 | 시퀀스, sha256로 식별
 │    └─ 라벨 개정 (Label revision)   항목마다 여러 개. 덮어쓰지 않고 쌓임
 │         · 라벨 공간 · 출처(import / 오토라벨 / 검수) · 날짜
 │         · 빠짐없이 라벨한 클래스 목록 (labelled classes)
 │         · 라벨 상태: 라벨 있음 | 배경
 └─ 데이터셋 계열 (Dataset)
      └─ 릴리스 (Release, 불변)        항목 목록 + 항목별 (split, 가리키는 라벨 개정)
           · 라벨 공간 · base 릴리스 · 메모 · 통계
```

| 결정 | 이유 |
|---|---|
| 라벨은 **개정으로 쌓고** 릴리스가 개정을 가리킨다 | 같은 이미지를 여러 릴리스가 서로 다른 라벨·라벨 공간으로 쓴다(od11 릴리스와 od18 릴리스가 한 이미지를 공유) |
| 개정마다 **빠짐없이 라벨한 클래스**를 기록 | 클래스가 늘어난 라벨 공간으로 옮길 때, 예전 개정에 없는 클래스를 "없음"으로 학습하면 안 된다. 학습 시 그 클래스를 무시하거나 오토라벨 대상으로 보낼 수 있다 |
| 라벨 상태 3가지를 구분 | "박스가 없는 이미지"가 배경 샘플인지 아직 안 본 것인지에 따라 학습에 넣을지가 갈린다 |
| 릴리스는 **base에서 파생**되고 서로 비교된다 | 추가/제거된 항목, 바뀐 개정, 클래스별 박스 수 변화가 릴리스 검토의 기본 |
| 항목 → 릴리스 **역참조** | 문제 있는 이미지를 발견했을 때 영향받는 릴리스를 바로 찾는다 |
| 사이트 · 카메라는 정해진 메타 필드 | 필터, 그룹 단위 split, 평가 슬라이스의 기준 |
| **시퀀스**를 항목 종류로 둔다 | 스켈레톤·동작 데이터셋이 이미 있다. 태스크 범위는 4장 참고 |
| 대량 조회는 서버 쪽에서 | 57만 장 릴리스를 페이지·필터·정렬. 릴리스 manifest와 항목 메타는 열 기반 저장(Lance)에 두고 통계는 릴리스 생성 때 미리 계산 |
| 큰 데이터는 **복사 없이 등록** | 수백 GB 단위 데이터셋이 흔하다. 저장 위치를 등록하고 sha256과 메타만 색인한다 (사내 Catalog의 릴리스를 옮겨 오는 것은 목표가 아니다) |

## 3. 화면

### 3.1 데이터셋

- **트리**: 계열 → 릴리스. 이름 검색, 태스크 필터, 펼치기/접기. 위쪽에 "모든 이미지 / 모든 시퀀스".
- **릴리스 화면**: 머리말(이름 · 버전 · 라벨 공간 · 날짜 · base) → 통계 타일(전체 · split별 수와 용량 · 라벨 있음 · 배경) → 클래스별 박스 수(접이식) · 메모 → 비교 → 필터(split · 라벨 상태 · 클래스 · 사이트 · 카메라 · 파일 이름 · 태그) → 그리드(파일 이름 · split · 박스 수/배경 · 해상도) · 보기 전환 · 페이지.
- **탭**: 샘플 / 클래스 / 분포 / 품질 / 모델 / 릴리스 비교.
- **항목 상세**: 큰 이미지 + 오른쪽 패널 — 오버레이 전환(단축키), 클래스 칩, **라벨 개정 목록**, **라벨 목록**(라벨마다 한 줄: 클래스와 클래스 안의 번호 · 놓인 곳 · 크기, 가리키면 그 라벨이 이미지에서 깜박임, 하나씩 끄기 — 0.50.1), 이미지 정보(크기 · 사이트 · 카메라 · split · sha256 · 파일), **포함된 릴리스 목록**, 이전/다음.
  - 사내 화면에 더하는 것: 개정 두 개를 나란히 또는 겹쳐 비교, 출처 배지(사람 / 오토라벨 / 합성), 같은 화면에서 검수(승인 · 거절 · 조정)로 전환, 비슷한 이미지 찾기.
- **릴리스 비교**: 항목 추가/제거, 개정이 바뀐 항목, 클래스별 박스 수 증감, split 이동. 결과를 필터로 걸어 그리드에서 바로 확인.
- **내보내기**: 릴리스 → YOLO · COCO 등, 클래스 부분집합 선택.

### 3.1a 카드 화면 (0.23.0)

Ultralytics의 카드 구성을 참고하되 BADAMOA의 묶음(폴더 → 프로젝트 → 데이터셋 계열 → 릴리스)에 맞췄다.
화면에서는 릴리스를 **버전**이라고 부른다(새 버전 · 이 버전으로 학습 · 버전 탭). 문서 · API · MCP의 이름은 release 그대로.

- 데이터셋 첫 화면: 폴더 칩(전체 · 폴더별 · 폴더 없음 · "+ 폴더") + 찾기 · 정렬, 프로젝트 카드(이미지 4장 콜라주에 박스, 태스크, 수, 최고 모델). 위쪽 버튼은 "새 프로젝트" 하나
- 필터 버튼 하나에 태스크와 클래스. 클래스는 많이 쓰는 것 + 이름 찾기로 고르고, 여러 개면 모두 들어 있는 프로젝트. 라벨이 실제로 있는 클래스만 센다(데이터셋마다 최신 버전). 걸린 조건은 칩으로 보이고 카드에 그 클래스의 라벨 수 (0.28.0)
- 폴더는 카드를 묶어 보는 칸일 뿐 데이터 · 학습 · 권한과 상관없다(만들고 고르는 곳마다 한 줄로 알린다). 이름은 따로 저장되어 비어도 남고, 고른 폴더에서 이름 바꾸기 · 지우기(안의 프로젝트는 "폴더 없음"으로) (0.27.0)
- 프로젝트 화면: 데이터셋 카드(최신 버전 기준) + 오른쪽에 모델 상위 5개
- 버전 화면: 위에 통계 타일, 아래 탭 — 이미지 · 클래스 · 통계 · 모델 · 버전. 탭은 주소(`#/datasets/<릴리스>/<탭>`)로 남아 공유된다
- 항목 보기의 라벨 개정은 번호(rev) 대신 그 개정을 담은 버전 이름으로 보인다
- 클래스 색은 라벨 공간에 저장(화면 표시용). 라벨 공간을 같이 쓰는 버전은 같은 색
- 통계는 버전당 최대 5,000장 표본으로 계산하고 표본 수를 함께 보인다

### 3.1b 등록한 뒤 다듬기 (0.24.0)

- 휴지통(왼쪽 메뉴 맨 아래, `#/trash`): 지운 프로젝트(만든 사람 · 관리자) · 데이터셋 버전(관리자) · 학습(시작한 사람 · 관리자) · 모델 · 모델 종류(관리자)를 숨겼다가 되살린다. 지운 것의 기록과 Hub 파일은 완전히 지우기 전까지 그대로다. 지운 프로젝트의 이름은 휴지통에 있는 동안 다시 쓸 수 없다(되살리기를 안내)
- 사이트 · 카메라는 이미지에 붙는 값이다. 0.24.0~0.49.0에는 파일 이름 규칙으로 채웠고, 0.50.1에 채우기를 뺐다. 이미 채운 값과 필터 · "같은 카메라끼리" split은 그대로 쓴다
- 클래스 바꾸기는 버전을 고치지 않고 새 버전을 만든다: 옛 클래스 번호 → 새 이름(같은 이름은 합침, 빈 이름은 뺌). 새 라벨 공간은 이름과 번호가 같은 것이 있으면 다시 쓰고, 라벨은 같은 내용의 개정이 있으면 다시 쓴다
- 항목 보기의 나란히 보기: 왼쪽은 고른 라벨, 오른쪽은 비교할 라벨. 클래스 목록이 다르면 색과 "이 버전의 클래스만"은 이름으로 맞춘다

### 3.1c 바로 고치기 · 작업 중 (0.38.0)

설계는 [LABELING_PLAN.md](LABELING_PLAN.md) 3장.

- 항목 보기 오른쪽 위의 "라벨 고치기"(E). 최신 버전과 작업 중에서만 열리고, 오래된 버전에는 이유와 "최신 버전 열기"를 보인다
- 고치는 동안 이미지 둘레에 강조색 테두리. 오른쪽에 도구(고르기 V · 박스 그리기 B), 클래스 목록(1~9, 12개가 넘으면 찾기), 되돌리기 · 다시 하기 · 지우기 · 배경으로, 저장 상태("저장됨 · 저장 안 됨")와 저장(Ctrl+S). ← →는 저장하고 넘긴다
- 고른 박스는 흰 점선과 여덟 손잡이. 겹친 박스는 누른 곳의 가장 작은 박스가 골라진다
- 작업 중이 있으면 그 데이터셋의 버전 화면 위에 "작업 중 · 고친 이미지 N장 — 열기" 띠, 버전 탭 맨 위에 "작업 중", 데이터셋 카드에 "작업 중 N"
- 작업 중 화면은 버전 화면과 같고, 제목 옆 "아직 버전 아님", 바탕 · 고친 수 · 고친 사람, "모두 되돌리기" · "버전으로 확정". 학습 · 내려받기 · 새 버전 · 삭제는 없다
- 이미지 그리드의 연필 표시와 "고친 것만" 필터(작업 중과 그 바탕 버전에서)
- 라벨 상태 "아직 안 함"은 타일 · 필터 · 배지로 보이고, 학습에서 빠진다
- (0.39.0) 분할: 고른 윤곽의 꼭짓점 손잡이, 선 두 번 누르기로 점 추가, "윤곽 그리기"는 첫 점(크게 표시)을 누르거나 Enter로 닫음

### 3.2 노드 자원

사내 모니터는 "서버 상태 감시" 화면이고, BADAMOA는 그 배치를 따르지 않는다(0.21.0에서 바꿈). BADAMOA의 노드 화면이
답하는 질문은 **"지금 GPU를 누가 쓰고, 내 학습은 어디서 언제 돌 수 있나"**이다.

- **GPU 자리표**(노드 목록): 모든 서버의 GPU를 한 판에 칸으로 놓는다.
  - 칸마다 주인을 적는다: BADAMOA 실행(이름 · epoch · 남은 시간, 누르면 그 실행) / 사람(사용자 · 프로그램) / 비어 있음 / 사람 전용.
  - 칸이 아래에서 차오른 높이가 GPU 메모리. 색은 주인(BADAMOA · 사람)만 나타낸다.
  - 맨 위에 빈 GPU 수와 주인별 수, 대기 중인 작업과 그 이유, 가장 먼저 끝날 학습.
  - 서버는 한 줄: 이름 · GPU 모델과 수 · CPU · RAM, 디스크는 90%를 넘을 때만.
- **GPU 타임라인**(서버 상세): GPU마다 가로 띠 하나에 6시간 · 24시간 · 7일. 그 GPU를 쓴 BADAMOA 실행과 사람이 이름 붙은 띠로,
  아래에 사용률(진할수록 높음). 그 위에 "지금" 한 줄(CPU · RAM · GPU 메모리 · 전력 · 업타임 · 디스크 경고).
- 그래프 9종과 사용자 · GPU · 디스크 · 물리 디스크 · 로그인 세션 표는 "자세한 그래프와 표"로 접어 둔다. 이 서버의 작업 목록은 펼친 채로.
- 그래프 조작은 Grafana에서 익숙한 것을 따른다(0.22.0): 드래그로 확대 · 더블클릭으로 되돌리기, 한 화면의 그래프와 타임라인이 같은 시각에 세로선을 맞추는 공유 십자선, 범례로 시리즈 고르기, 새로고침 버튼과 자동 새로고침 간격. Grafana 자체는 설치하지 않고, 사내에 있으면 `/metrics`로 가져가게 한다.
- **수집 항목**(Node Agent): CPU 사용률 · load · 온도 · 전력, 메모리, GPU별 사용률 · 메모리 · 온도 · 전력 · 프로세스(사용자), 마운트별 디스크, 물리 디스크 I/O, 사용자별 CPU · 메모리 · GPU, 로그인 세션, 업타임.
- **이력 저장**: 1분 평균 → 10분 → 1시간으로 단계별로 줄여 30일 보관. Hub의 SQLite에 두되 원본 해상도는 짧게만 유지.

### 3.2a 학습할 노드 (0.37.0)

- 새 학습 · 탐색 창의 "학습할 노드"는 기본이 **자동**(이미지가 있는 노드)이다. "노드 고르기"를 고르면 노드마다 한 줄: 상태 점 · 이름 · 빈 GPU · "이미지 있음 / 받아 둠 / 받아야 함 N GB". 작업을 받지 않는 노드와 0.37.0 전의 노드(받을 수 없음)는 고를 수 없다.
- 고른 노드에 이미지가 있으면 "이미지가 있는 …에서 학습합니다", 없으면 "…가 먼저 …에서 N장(N GB)을 직접 받은 뒤 학습합니다. 받는 동안 GPU는 잡지 않고, 한 번 받으면 다음부터는 바로 시작합니다". 보관 위치의 남은 공간이 모자라면 그 자리에서 알린다.
- 학습 화면의 진행 단계는 이미지를 받아야 할 때 "대기" 대신 "이미지 받기"로 시작하고, 받는 동안 진행률(% · GB · MB/s · 남은 시간)을 보여 준다.
- 노드 설정(관리자)의 "받은 이미지 보관 위치": 자동 · 디스크(남은 / 전체) · 직접 입력. 받아 둔 이미지 수 · 크기와 이미지 전송 포트 상태를 함께 보여 준다.

### 3.3 공유 서버와 함께 쓰기

서버를 여러 사람이 직접 쓰고 있으므로 BADAMOA가 GPU를 독점한다고 가정할 수 없습니다.

| 결정 | 내용 |
|---|---|
| 배정 단위는 **GPU** | 작업은 "GPU n개 · VRAM 최소 x"를 요구하고, 노드는 받은 GPU만 보이게 해서 실행한다 |
| 남이 쓰는 GPU는 **바쁜 것으로 본다** | 다른 프로세스가 메모리를 잡고 있거나 사용률이 높으면 배정하지 않는다. 기준값은 설정 |
| 점유자를 보여 준다 | GPU마다 BADAMOA 작업 / 사용자 프로세스 / 비어 있음 |
| 사람 전용 | 관리자가 노드 설정에서 GPU를 사람 전용으로 두면 BADAMOA는 그 GPU에 작업을 보내지 않는다(0.21.0) |
| 대기 사유를 보여 준다 | 작업이 대기 중이면 "조건에 맞는 빈 GPU 없음"처럼 이유를 표시 |

## 4. 정해진 것과 남은 것

정해진 것:

- **사내 Dataset Catalog와 서버 모니터는 참고만 한다.** 대체·흡수·데이터 이전은 하지 않는다. 따라서 기존 릴리스를 가져오는 전용 도구는 만들지 않고, 일반 포맷(COCO · YOLO 등) 가져오기와 폴더 등록만 지원한다.
- **노드 지표는 BADAMOA Node Agent가 직접 수집한다.** 서버에 이미 도는 모니터 에이전트와는 무관하게 동작하고, 그 값을 받아 쓰지 않는다.
- 릴리스 이름과 라벨 공간 이름은 BADAMOA가 규칙을 강제하지 않는 자유 문자열로 둔다.

남은 것:

- **태스크 범위**: 스켈레톤·동작·모션 데이터셋(시퀀스)의 학습·평가까지 BADAMOA에서 할지. 지금 계획은 탐지 · 분할 · 분류 기준이고, 시퀀스는 데이터 모델에 자리만 마련해 둔다.

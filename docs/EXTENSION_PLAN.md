# 확장 계획 — 태스크 · 데이터 형식 · 모델 · 지표 · 환경

많이 쓰는 데이터 형식 · 모델 · 평가 지표는 처음부터 들어 있다.
팀이 만든 형식 · 모델 · 지표도 등록하면 같은 화면에서 클릭으로 쓴다.
등록한 것은 **실제로 돌려 보고 통과해야** 쓸 수 있다.

**진행 상태**: 계획 (0.39.0 기준). 정할 것은 11장.
[EXECUTION_PLAN.md](EXECUTION_PLAN.md) 2장(모델 템플릿) · 3장(환경)을 넓힌다. Docker의 방식(EXECUTION_PLAN 3.3 · 8장)은 이 문서 7장이 바꾼다.

## 1. 한눈에 — 태스크가 축이다

```
                  ┌──────────── 태스크: 라벨과 예측의 모양 ────────────┐
 폴더 ─[형식: 읽기]→ 라벨 ─[형식: 쓰기]→ 학습 데이터 ─[모델: train]→ 모델
                    │                                               │
                    └──── 정답 ──→ [지표] ←── 예측 ←──[모델: predict]┘
                                    │
                                   점수
```

| 등록하는 것 | 정하는 것 | 기본 제공 예 | 팀이 만드는 예 |
|---|---|---|---|
| **태스크** | 라벨 하나의 모양(박스 · 윤곽 · 점 · 클래스 · 속성), 예측의 모양, 대표 지표 | Det · Seg · Kpt · Cls | OCR(박스 + 글자), 불량 등급(이미지마다 숫자) |
| **데이터 형식** | 폴더를 라벨로 읽는 법, 학습 코드가 읽는 모양으로 쓰는 법 | YOLO · COCO · 클래스별 폴더 | 사내 검사기 JSON, CSV 목록 |
| **모델** (템플릿) | 학습 · 예측 · 내보내기 코드, 설정 항목, 환경 | YOLO · torchvision | 사내 RT-DETR, 사내 OCR |
| **지표** | 정답과 예측으로 점수를 내는 코드, 높을수록 좋은지 낮을수록 좋은지 | COCO mAP · Top-1 · F1 | 오검출 1% 기준 불량 검출률, CER |

- 넷은 **태스크 이름으로 짝지어진다.** 버전을 고르면 그 태스크의 모델만, 평가에서는 그 태스크의 지표만 나온다. 사람이 짝을 맞추지 않는다.
- 형식 · 모델 · 지표는 같은 방식으로 등록한다. 선언 파일 + 코드를 zip이나 CLI로 올리고, 버전이 쌓이고, 시험 실행을 통과해야 쓸 수 있다 (8장).
- 태스크에는 코드가 없다. 관리자 설정의 **폼**으로 만든다. 형식이나 모델의 묶음에 선언을 넣어 함께 올려도 된다.

## 2. 지금과 바뀌는 것

| | 지금 (0.39.0) | 바뀐 뒤 |
|---|---|---|
| 태스크 | 기본 4개 + 이름만 적는 팀 태스크. 라벨 모양을 모른다 | 팀 태스크도 모양을 등록한다. 화면 · 검사 · 변환이 그 모양을 안다 |
| 데이터 형식 | 코드에 박힌 것만: 가져오기 YOLO · COCO · 클래스별 폴더, 학습용 yolo · yolo-seg · imagefolder | 기본 형식을 넓히고, 팀 형식을 등록한다 |
| 모델 | 템플릿을 등록. 선언만 검사 | 시험 실행을 통과한 것만 쓴다 |
| 지표 | 템플릿의 eval 코드가 각자 계산한다. 템플릿이 다르면 같은 이름(mAP)도 계산법이 다를 수 있다 | **지표가 따로 있다.** 모델은 예측만 내고, 같은 지표 코드가 모든 모델을 채점한다. 팀 지표도 등록한다 |
| 환경 | 자동 설치(uv) · 서버의 Python | 선언은 하나, 노드가 가상환경이나 컨테이너로 만든다 (7장) |

읽으면서 찾은 것 (1단계에서 먼저 고친다):

- **학습 코드가 노드 토큰을 받는다.** 노드는 작업 프로세스의 환경 변수를 그대로 학습 · 평가 코드에 넘긴다(`node/trainer.py`, `node/modelops.py`의 `{**os.environ}`). 올린 코드가 `BADAMOA_NODE_TOKEN`으로 Hub의 노드 API를 부를 수 있다.
- **팀 태스크의 라벨 값이 그대로 남지 않는다.** YOLO 라벨을 읽을 때 값 개수로 윤곽인지 추측한다(`node/importer.py`의 `_read_yolo_label`). `0 cx cy w h a b`는 윤곽으로 읽혀 박스가 바뀌고, `0 cx cy w h a`는 `a`가 버려진다.
- **Kpt는 학습 형식이 없다.** 태스크가 `pose`인 템플릿은 등록되지만 학습이 노드에서 실패한다.
- **팀 태스크에는 대표 지표가 없다** (`training.PRIMARY_METRIC`). 모델 순위의 기준이 없다.

## 3. 태스크

### 3.1 모양 선언

```toml
name  = "OCR"
title = "문자 인식"

[object]                          # 이미지 안의 물체 하나
shape = "box"                     # box | outline | points | rotated-box | none
classes = true
attributes = { text = "text" }    # text · number · choice:[…] · file

[image]                           # 이미지 하나에
attributes = {}                   # 예: { grade = "number" }

[metrics]
primary = "cer"                   # 순위 · "가장 좋은 모델"의 기준
goal = "min"                      # 작을수록 좋음
```

기본 태스크도 같은 틀로 적힌다.

| 태스크 | object.shape | 속성 | 대표 지표 | 상태 |
|---|---|---|---|---|
| Det | box | — | map50_95 | 있음 |
| Seg | outline | — | mask_map50_95 | 있음 |
| Kpt | points (라벨 공간의 점 이름 · 연결선) | — | OKS mAP | 가져오기 · 보기 있음, 학습 계획 |
| Cls | none (이미지에 클래스 하나) | — | top1 | 있음 |
| 회전 박스 (OBB) | rotated-box | — | map50_95 | 계획 |
| 의미 분할 | — | image: `mask = "file"` | miou | 계획 (파일 속성 뒤) |

### 3.2 저장 — 카탈로그를 크게 바꾸지 않는다

- shape는 지금의 숫자 행 `[클래스, cx, cy, w, h, …]` 그대로다. 윤곽 · 점 · 각도가 박스 뒤에 붙는다.
- 속성은 행 옆의 속성 목록에 둔다. LABELING_PLAN 3B의 "박스 속성"과 같은 자리다. 이미지 속성은 라벨 개정에 이미지 단위로 둔다.
- 파일 속성(마스크 PNG, 깊이 지도)은 이미지처럼 복사 없이 해시로 등록한다. 가장 큰 변경이라 마지막에 한다 (10장 7단계).

### 3.3 규칙

- 태스크의 모양은 **늘리기만** 한다(선택 속성 추가). 바꾸거나 빼려면 새 이름을 쓴다. 그래야 이미 등록된 형식 · 모델 · 지표가 깨지지 않는다.
- 태스크마다 다른 화면을 만들지 않는다. 그리기는 shape로 하고(지금의 박스 · 윤곽 · 점), 속성은 항목 보기의 목록에 글자로 보인다.
- 지금 이름만 있는 팀 태스크는 "박스 + 뒤의 숫자 값"인 태스크로 옮긴다.

### 3.4 예측의 모양

모델의 predict는 **라벨과 같은 모양 + 확신도**를 낸다. SDK가 지금 Det(`boxes`) · Cls(`top`)에 쓰는 모양을 태스크 전체로 넓힌다.

```json
{"image": "0001.jpg", "rows": [[0, 0.91, 0.51, 0.62, 0.20, 0.08]], "attributes": [{"text": "12가3456"}], "image_attributes": {}}
```

이미지가 많으므로 한 장씩 보낸다: `bm.prediction(image, rows=…, attributes=…)`. 노드가 JSON Lines 파일로 모은다.

## 4. 데이터 형식

### 4.1 기본 제공

| 형식 | 태스크 | 가져오기 | 학습용으로 쓰기 | 내려받기 |
|---|---|---|---|---|
| YOLO | Det · Seg · Kpt | ✅ | Det ✅ · Seg ✅ · Kpt 계획 | ✅ |
| COCO JSON | Det · Seg · Kpt | ✅ (RLE 마스크 제외) | 계획 (내려받기 코드를 다시 씀) | ✅ |
| 클래스별 폴더 | Cls | ✅ | ✅ | ✅ |
| Pascal VOC XML | Det | 계획 | 계획 | 계획 |
| CSV (이미지, 클래스) | Cls (한 장에 여러 클래스 포함) | 계획 | 계획 | 계획 |
| YOLO OBB · DOTA | 회전 박스 | 계획 | 계획 | — |
| 마스크 PNG (VOC · Cityscapes 방식) | 의미 분할 | 계획 (파일 속성 뒤) | 계획 | — |
| manifest (JSON Lines) | 모든 태스크 | — | 계획: 라벨 값을 그대로 | 계획 |
| CVAT · Label Studio | Det · Seg · Kpt | Phase 3 (LABELING_PLAN) | — | Phase 3 |

**manifest**는 모든 태스크의 출구다. 이미지는 지금처럼 원본을 가리키는 링크로 두고, 라벨은 저장된 값 그대로 한 줄에 한 이미지로 적는다.

```
data/
  dataset.json      {"schema": 1, "task": "OCR", "classes": ["plate", "char"], "splits": {"train": 96, "val": 24}}
  manifest.jsonl    {"image": "images/train/3f9a….jpg", "split": "train", "name": "cam1/0001.jpg",
                     "rows": [[0, 0.51, 0.62, 0.20, 0.08]], "attributes": [{"text": "12가3456"}]}
  images/<split>/…
```

### 4.2 팀 형식 등록

```
inspector-json/
  badamoa-format.toml
  read.py       폴더 → 이미지와 라벨 (필수)
  write.py      버전 → 팀 학습 코드가 원래 읽던 폴더 모양 (선택)
  sample/       시험용 작은 폴더 (필수, 5 MB 이하)
```

```toml
name    = "inspector-json"
title   = "검사기 JSON"
version = "1.0.0"
task    = "DefectGrade"               # 등록된 태스크
detect  = ["**/*.inspect.json"]       # 가져오기 창에서 "이 형식 같습니다"를 띄우는 파일 모양
```

```python
import json
import badamoa_sdk as bm

for path in bm.source().glob("**/*.inspect.json"):
    d = json.loads(path.read_text(encoding="utf-8"))
    bm.item(path.parent / d["image"], split=d.get("split", "train"),
            rows=[[o["cls"], *o["xywh"]] for o in d["defects"]],
            attributes=[{"grade": o["grade"]} for o in d["defects"]])
```

- `read.py`는 "어느 이미지에 어떤 라벨"만 알린다. 이미지 해시 · 썸네일 · Hub로 올리기는 지금의 가져오기 코드가 그대로 한다.
- 데이터 쪽은 환경이 가볍다. `read.py`는 **노드의 Python**(표준 라이브러리 + SDK)으로 돈다. 패키지가 필요하면 `requirements`를 적고 작은 가상환경이 만들어진다. Docker는 쓰지 않는다.
- `write.py`가 없으면 학습용으로는 manifest로 푼다. 있으면 팀 학습 코드가 원래 읽던 모양 그대로 받는다 — **사내 코드의 데이터 로더를 고치지 않아도 된다.**
- 모델의 `data_format`에 등록한 형식 이름을 적을 수 있다 (`write.py`가 있을 때).

## 5. 모델 (템플릿)

지금의 템플릿(EXECUTION_PLAN 2장, `badamoa_sdk`)을 그대로 쓰고 아래를 바꾼다.

- `task`는 등록된 태스크, `data_format`은 기본 형식 · 등록한 형식 · manifest 중 하나다. 짝은 등록할 때 검사한다 (8.2).
- **`predict`가 평가의 입구가 된다.** 평가는 predict로 예측을 내고 지표가 채점한다 (6.3). predict가 없는 모델은 학습 중 보고한 지표만 있고 평가 · 비교 · 순위에서 빠진다.
- `eval`은 선택이다. 템플릿 자체 지표(예: Ultralytics val)를 빨리 보고 싶을 때 쓴다. 모델 비교와 순위는 지표의 점수로 한다.
- 받는 데이터의 조건을 적는다. 학습을 시작하기 전에 고른 버전과 맞춰 본다 (9.2).

```toml
[data]
classes = { min = 2 }     # 클래스 수 범위. 분류는 기본 min = 2, 그 밖은 1
min_images = 8            # 학습에 들어갈 라벨 있는 이미지의 최소 (기본 1)
keypoints = 17            # Kpt: 점 개수가 정해진 모델이면 (0 = 아무 개수)
attributes = ["text"]     # 이 모델이 읽는 속성. 태스크에 없으면 등록 거부
```

## 6. 지표

### 6.1 기본 제공 — 잘 알려진 라이브러리로

| 태스크 | 지표 | 라이브러리 |
|---|---|---|
| Det | mAP50-95 · mAP50 · 크기별 AP · 클래스별 AP, 확신도 기준 P · R · F1, 혼동 행렬 | pycocotools (또는 호환되는 faster-coco-eval) |
| Seg | mask mAP | 같음 |
| Kpt | OKS mAP | 같음 |
| Cls | Top-1 · Top-5, 매크로 P · R · F1, 혼동 행렬 | scikit-learn |
| 의미 분할 | mIoU · 픽셀 정확도 | numpy |
| 숫자 속성 (회귀) | MAE · RMSE | numpy |
| 글자 속성 | CER · WER | jiwer |

지표는 CPU로 가볍게 돈다. 작은 가상환경(PyTorch 없음)이면 된다.

### 6.2 팀 지표 등록

```
recall-at-fp/
  badamoa-metric.toml
  metric.py
```

```toml
name    = "recall-at-fp"
title   = "오검출 1% 기준 불량 검출률"
version = "1.0.0"
task    = "detect"            # 기본 태스크에도 팀 지표를 더할 수 있다
goal    = "max"
primary = "recall_at_fp1"
requirements = ["numpy"]
```

```python
import badamoa_sdk as bm

truth, preds = bm.truth(), bm.predictions()   # 태스크 모양의 정답과 예측 (이미지별)
...
bm.finish({"recall_at_fp1": value}, classes=per_class, images=per_image)
```

- 지표 하나가 숫자 여러 개를 낼 수 있다. `primary`가 대표다.
- 이미지별 값(`images`)은 "라벨 의심 순" 정렬(LABELING_PLAN 3.3)에 그대로 쓰인다.
- 프로젝트 설정에서 태스크마다 **기본 지표**를 고른다. 모델 순위와 "가장 좋은 모델"이 그것을 따른다.

### 6.3 평가 흐름

```
평가 → 버전 · split → [모델 predict] → 예측 파일 → [지표 A] [지표 B] … → 평가 기록
```

- 한 작업(`model.run`) 안에서 이어서 돈다. predict는 모델의 환경(GPU 가능), 지표는 지표의 환경(CPU).
- **예측 파일은 Hub에 남는다.** 지표를 새로 등록하면 다시 predict하지 않고 남은 예측으로 채점만 한다. 지난 모델들도 새 지표로 바로 비교된다.
- 학습이 끝나면 val을 predict하고 기본 지표로 채점해 모델의 점수로 둔다 (Q3). 템플릿이 달라도 같은 계산법으로 순위가 매겨진다.

## 7. 환경 — Docker에 대한 의견

질문: 데이터 쪽은 환경 의존이 낮고 학습 · 평가는 환경이 중요하다. 원격 학습 서버를 생각하면 환경을 Docker로 가져야 하지 않나.

**의견: 방향은 맞다. 원격 Linux GPU 서버의 학습 · 예측은 컨테이너를 기본으로 하자.**
다만 Docker 이미지를 환경의 "정의"로 삼지 않고 "실행 수단"으로 삼는다. 정의는 선언 하나(패키지 목록 · 베이스 이미지 · 시스템 패키지)에 두고, 노드가 자기 능력에 맞게 컨테이너나 가상환경으로 만든다.
이 PC에는 Docker Desktop(NVIDIA 런타임)과 사내 레지스트리에서 받은 학습 이미지가 이미 있다. 팀이 컨테이너로 학습하는 데 익숙하다면 더 그렇다.

### 7.1 두 방식 비교

| | 가상환경 (uv) | 컨테이너 (Docker) |
|---|---|---|
| 같은 환경 | 패키지 버전까지 (고정 목록이 있으면 정확히). OS 라이브러리 · CUDA 런타임은 서버 것 | OS · CUDA 런타임까지. 다이제스트로 그대로 재현 |
| 시스템 패키지 · 컴파일이 필요한 연산 (libGL, ffmpeg, mmcv, deformable attention) | 서버에 깔려 있어야 한다 | 이미지 안에 있다 |
| 올린 코드 가두기 | 노드 사용자 권한 그대로 | 마운트한 폴더만 보인다. 토큰 · 네트워크를 막을 수 있다 |
| Windows 서버 | 된다 | Docker Desktop · WSL2가 있어야 한다 |
| 서버 준비 | uv 하나 (자동) | Docker + NVIDIA Container Toolkit |
| 크기 | PyTorch 포함 수 GB, uv 캐시로 공유 | 베이스 이미지 수 GB ~ 10 GB 넘음, 층으로 공유 |
| 폐쇄망 | PyPI 미러가 있어야 한다 | 레지스트리가 있으면 된다 (이미 있음) |
| 만드는 사람의 일 | requirements 한 줄 | Dockerfile을 써야 하면 "클릭 클릭"이 깨진다 → 7.2처럼 BADAMOA가 만든다 |

### 7.2 제안

1. **선언은 하나.** 템플릿의 `[environment]`에 지금처럼 `requirements`를 적고, 필요하면 `base`(베이스 이미지) · `system`(apt 패키지) · `image`(팀이 이미 만든 이미지)를 더한다.
2. **이미지는 환경만 담는다. 코드는 담지 않는다.** 템플릿 코드는 지금처럼 Hub에서 받아 해시로 캐시하고 컨테이너에 마운트한다. 코드만 고친 새 버전은 이미지를 다시 만들지 않는다. 10 GB 넘는 이미지를 버전마다 만들지 않아도 된다.
3. **이미지는 BADAMOA가 만든다.** `image`가 없으면 노드가 `base` 위에 `system` · `requirements`를 설치하는 Dockerfile을 만들어 한 번 빌드하고, 선언의 해시로 이름을 붙여 다시 쓴다. 레지스트리를 설정해 두면 거기에 올려 다른 서버는 받기만 한다. 묶음에 `Dockerfile`이 있으면 그것을 쓴다. `image`를 적으면(예: 사내 레지스트리의 학습 이미지) 그대로 쓴다.
4. **노드가 고른다.** Docker가 되는 서버는 컨테이너로, 아닌 서버(Windows 개발 PC 등)는 가상환경으로 같은 선언을 실행한다. `system` · `image` · `Dockerfile`이 있는 템플릿은 컨테이너가 되는 서버에만 배정하고, 없으면 대기 사유로 알린다.
5. **가상환경도 같은 버전으로.** 시험 실행(8장)에서 설치된 패키지 목록(`name==version`)을 템플릿 버전에 고정하고, 다른 서버도 그 목록으로 설치한다. PyTorch는 버전만 고정하고 CUDA 빌드는 서버 드라이버에 맞춘다. 이것만으로 "서버마다 버전이 다르다"는 문제의 대부분이 사라진다.
6. **데이터 쪽 · 지표는 컨테이너를 쓰지 않는다.** 형식 읽기는 노드의 Python, 지표는 작은 가상환경이면 된다. 그래서 데이터만 다루는 서버에는 Docker가 필요 없다.
7. **가두기는 어느 방식이든.** 학습 · 평가 코드에 노드 토큰을 넘기지 않는다. 컨테이너에는 작업 폴더 · 원본 이미지 폴더(읽기 전용) · 캐시만 마운트한다. 네트워크는 관리자 정책으로 둔다(사전학습 가중치를 받으려면 필요하다).
8. 사용자 화면에는 나오지 않는다. 관리자 설정에 "Docker가 되는 서버에서는 컨테이너로"(기본 켬)와 레지스트리 주소만 둔다.

EXECUTION_PLAN 3.3의 처리할 것(GPU 장치 제한, 원본 폴더를 같은 경로로 읽기 전용 마운트, 컨테이너 사용자 맞추기, 취소는 컨테이너 중지, 다이제스트 기록)은 그대로 쓴다.
EXECUTION_PLAN 8장의 "자체 이미지 빌드는 하지 않는다"는 바꾼다: 선언에서 만드는 이미지와 묶음의 Dockerfile까지는 BADAMOA가 빌드한다.

## 8. 등록과 확인 — 세 종류 공통

### 8.1 흐름과 상태

```
올림 → 정적 검사 → "확인 중" → 시험 실행 (서버 한 대, 기본 CPU) → "쓸 수 있음" 또는 "실패: 이유"
```

| 상태 | 뜻 | 일반 사용자 화면 | 관리자 설정 |
|---|---|---|---|
| 확인 중 | 시험 실행 대기 · 진행 | 안 보임 | 지금 단계 |
| 쓸 수 있음 | 통과 | 보임 | 마지막 확인: 날짜 · 서버 · 환경 · 걸린 시간 |
| 실패 | 한 단계가 실패 | 안 보임 | 실패한 단계, 한 문장 이유, 로그 |
| 확인 못 함 | 돌릴 서버가 없음 | 안 보임 | 이유와 "다시 확인" |
| 허용 | 관리자가 이유를 적고 확인 없이 허용 | 보임 | 누가 · 언제 · 이유 (감사 로그) |

- 상태는 **버전마다** 있다. 새 버전이 확인 중이거나 실패하면 화면은 그것의 **마지막으로 통과한 버전**을 쓴다. 새 버전을 올리다 실패해도 쓰던 것이 사라지지 않는다.
- 기본 제공은 BADAMOA를 내기 전에 확인하므로 처음부터 "쓸 수 있음"이다.
- 시험 실행은 GPU를 잡지 않는다. CPU로 돌 수 없는 모델만 `[check] gpu = true`로 GPU 1장을 짧게 쓴다.

### 8.2 무엇을 검사하나

| 종류 | 정적 검사 (Hub, 올릴 때) | 시험 실행 (노드) | 통과 기준 |
|---|---|---|---|
| 데이터 형식 | 선언, 태스크가 있는지, 모든 .py 문법(`ast.parse`, 실행하지 않음), `sample/` | `sample/`을 read → `write.py`가 있으면 쓰고 다시 read | 항목 1개 이상, 라벨이 태스크 모양에 맞음, 쓰고 다시 읽어도 라벨이 같음 |
| 모델 | 진입점이 가리키는 .py가 있는지, 모든 .py 문법, 태스크와 형식의 짝, `[data]`의 속성이 태스크에 있는지, requirements 표기(`packaging`) | 시험 데이터를 모델의 형식으로 풀어 train → predict → (eval · export) | 종료 코드 0, 가중치 파일, 지표 1개 이상, 이미지마다 예측 한 줄, 선언한 진입점이 모두 결과를 냄 |
| 지표 | 선언, 태스크가 있는지, .py 문법 | 샘플 정답을 그대로 예측으로 넣기, 빈 예측 넣기 | 정답 그대로 → 가장 좋은 값(mAP 1.0, CER 0), 빈 예측 → 가장 나쁜 값 |

모델이 통과는 하지만 알리는 것: 태스크의 대표 지표를 보고하지 않음, `resume = true`인데 체크포인트를 알리지 않음.
지표 값이 그럴듯한지는 보지 않는다. 열두 장으로 1 epoch 학습한 지표는 의미가 없다.

### 8.3 시험 데이터

| 출처 | 언제 | 내용 |
|---|---|---|
| 내장 합성 샘플 | 기본 태스크 | 노드가 그 자리에서 만든다(Pillow). 색 사각형과 그 박스 · 윤곽 · 점, 분류는 클래스마다 다른 색. train 8 · val 4장, 160 px. 폐쇄망에서도 된다. `tests/sample_data.py`를 패키지로 옮겨 쓴다 |
| 함께 올린 샘플 | 팀 태스크는 필수, 기본 태스크는 있으면 먼저 | 모델 · 지표는 묶음의 `check/`, 형식은 `sample/`. 5 MB 이하 |
| 고른 데이터 버전의 일부 | 관리자가 "이 데이터로 확인"을 누를 때 | train 16 · val 8장. 실제 해상도 · 라벨 모양으로 보고 싶을 때 |

### 8.4 짧게 돌리기

```toml
[check]
params = { epochs = 1, imgsz = 64, model = "yolo11n.pt" }   # 시험 실행에서만 쓰는 설정 값
timeout_min = 15        # 환경 준비를 뺀 시간
gpu = false
skip = []               # 시험하지 않을 진입점. 예: ["export"]
```

- `[check]`가 없으면 설정은 기본값이고, `epochs`라는 설정이 있으면 1로 둔다.
- config에 `"check": true`가 들어간다. 코드는 SDK의 `run.check`로 읽어 몇 step 만에 멈출 수 있다.
- 환경 준비는 실제 학습과 같은 경로다. 시험 실행 때 설치 · 빌드한 가상환경과 이미지를 그 서버의 학습이 그대로 쓴다.

### 8.5 다시 확인할 때

| 일 | 동작 |
|---|---|
| 새 버전을 올림 | 그 버전만 확인 |
| 같은 내용(같은 해시)을 다시 올림 | 앞 결과를 그대로 |
| 환경이 바뀜 (등록된 Python의 경로, 이미지 다이제스트) | 뒤에서 다시 확인. 결과가 나올 때까지 지금 상태 유지 |
| BADAMOA가 약속(config · 형식 · SDK)을 바꿈 | 약속 번호(`CONTRACT`)가 올라가면 모두 뒤에서 다시 확인 |
| 실제 학습이 성공 | "확인 못 함" · "허용"이던 버전은 "쓸 수 있음"으로 |
| 실제 학습이 실패 | 바꾸지 않는다. 데이터나 설정 탓일 수 있다 |

### 8.6 Hub에 남는 것

**코드는 Hub에 남고, 환경은 "무엇이 깔렸는지"만 남는다.** 환경 자체(가상환경 폴더, 이미지)는 수 GB이고 OS마다 달라서 Hub에 두지 않는다. 대신 같은 환경을 다시 만들 수 있을 만큼 기록한다.

| 무엇 | 지금 (0.39.0) | 바뀐 뒤 |
|---|---|---|
| 모델 코드 | 올린 zip이 Hub 저장소에 해시로, 버전마다. 선언은 DB에. 노드는 Hub에서 받아 캐시 | 그대로 + 관리자 화면에서 버전별 내려받기 |
| 형식 · 지표 코드 | (아직 없음) | 모델과 같다: zip을 해시로, 버전마다, 샘플 포함 |
| 태스크 | 이름만 데이터셋에 | 모양 선언이 DB에, 늘린 기록과 함께 |
| 환경의 선언 | 템플릿 선언 안의 `[environment]` | 그대로 |
| 실제로 깔린 것 | 실행마다 패키지 목록(`name==version`)을 실행 기록에 | + 시험 실행의 패키지 목록을 템플릿 버전에 고정. 다른 서버도 그 목록으로 설치 |
| 컨테이너 이미지 | (아직 없음) | 이미지는 레지스트리에, Hub에는 이름과 다이제스트 |
| 서버의 기존 Python | 서버별 경로와 "연결 확인" 결과 | 그대로 + 실행마다 패키지 목록 (지금도 남음) |
| SDK | BADAMOA에 들어 있고 실행 때 노드가 넣어 줌. 실행 기록에 버전이 남지 않음 | 실행 기록에 SDK 버전과 약속 번호 |
| 어느 형식으로 읽었나 | 가져오기 기록에 형식 이름만 (`yolo` · `coco`) | 형식 이름 · 버전 · 코드 해시. 계보에 "데이터 버전 ← 형식 버전" |
| 내 PC의 `template check --run` | — | Hub에 남지 않는다. 올린 것만 남는다 |

그래서 "이 모델은 어떤 코드로, 어떤 패키지로, 어떤 형식으로 읽은 데이터로 만들었나"를 Hub만 보고 답할 수 있고, 같은 템플릿 버전 · 같은 패키지 목록(또는 다이제스트)으로 다시 실행할 수 있다.

## 9. 쓰는 사람의 화면 — 클릭으로

### 9.1 흐름

| 하는 일 | 사용자가 하는 것 |
|---|---|
| 가져오기 | 폴더를 고른다 → 맞는 형식이 골라져 있다(여럿이면 고른다) → 태스크가 따라온다 → 가져오기 |
| 학습 | 버전을 고른다 → 그 태스크의 모델만 보인다 → 프로젝트가 기억한 지난 모델 · 설정이 채워져 있다 → 시작 |
| 평가 | 모델 → 평가 → 버전 · split → 그 태스크의 기본 지표가 골라져 있다 → 시작 |
| 다음 학습 | 프로젝트가 태스크마다 마지막 모델 · 설정을 기억한다. "설정 저장"으로 이름 붙인 묶음(예: "야간 검출 기본")을 만들어 고른다 |
| 등록 | 설정 → 확장: 태스크(폼) · 데이터 형식 · 모델 · 지표(zip 올리기). 시험 실행 단계가 보이고, 통과하면 위 화면들에 바로 나온다 |

사용자 화면에는 "시험 실행", "환경", "Docker", "확인 중" 같은 말이 나오지 않는다. 쓸 수 없는 것은 보이지 않을 뿐이다.

### 9.2 시작 전 검사

Hub가 버전의 통계로 계산한다. 노드에 묻지 않는다. 막히면 **시작 버튼 아래 한 줄**로 이유와 할 일을 보여 주고 버튼을 끈다. 알림은 작은 글씨로 둔다.

| 검사 | 결과 | 메시지 예 |
|---|---|---|
| 태스크가 다름 | 막음 (지금 있음) | 이 모델은 Det용이고 이 데이터셋은 Cls입니다 |
| 모델 · 지표가 확인을 통과하지 않음 | 막음 | 이 모델은 아직 확인되지 않았습니다. 관리자에게 문의하세요 |
| 학습할 서버가 그 형식이나 컨테이너를 못 씀 | 막음 | 이 모델을 돌릴 수 있는 서버가 지금 없습니다 |
| 클래스 수가 `[data] classes` 밖 | 막음 | 이 모델은 클래스가 2개 이상이어야 합니다. 클래스를 더 고르세요 |
| 라벨 있는 이미지 < `min_images` | 막음 | 학습에 쓸 라벨 있는 이미지가 3장입니다 (8장 필요) |
| Kpt 점 개수가 다름 | 막음 | 이 모델은 점 17개를 받습니다. 이 데이터셋은 5개입니다 |
| val split이 없음 | 알림 | val이 없어 train의 20%를 검증에 씁니다 |
| 분류: train에 이미지가 없는 클래스 | 알림 | `dog` 클래스는 train에 이미지가 없습니다 |

API · MCP · 탐색 · 다시 실행도 같은 검사를 한다. 대화상자용으로 시작하지 않고 검사만 하는 API를 둔다.

## 10. 구현 순서

각 단계는 그것만으로 쓸 수 있게 끝낸다. 확인은 가볍게 한다 (합성 샘플, COCO128, 가장 작은 YOLO).

| 단계 | 내용 | 확인 방법 | 이 PC |
|---|---|---|---|
| **1** 바로 고칠 것과 검사 | 학습 코드에 노드 토큰을 넘기지 않음, 팀 태스크 가져오기의 값 보존, 모델의 정적 검사, 시작 전 검사와 대화상자 안내 | 잘못된 묶음 거부, 클래스 1개짜리 분류 버전으로 시작 거부, 템플릿 코드에서 토큰이 안 보임 | 가능 |
| **2** 모델 시험 실행 | `template.check` 작업, 합성 샘플, `[check]`, 상태와 마지막 통과 버전, 관리자 화면, 패키지 고정 목록, `template check --run` · `push --wait` | `dummy`로 통과 · 실패, YOLO11n CPU 시험 실행 | 가능 |
| **3** 지표 분리 | 예측 모양(`bm.prediction`), predict로 평가, 기본 지표, 예측 파일 보관과 다시 채점, 팀 지표 등록 · 시험, 학습 뒤 자동 채점 | YOLO11n과 Faster R-CNN을 같은 지표로 채점해 비교, 새 지표를 등록하고 predict 없이 채점 | 가능 |
| **4** 태스크 등록 | 태스크 폼 · 모양 선언, 속성 저장(LABELING_PLAN 3B와 함께), manifest 형식, 기존 팀 태스크 옮기기 | 박스 + 글자 속성의 작은 OCR 태스크로 가져오기 → 학습 → CER 채점 | 가능 |
| **5** 데이터 형식 | 팀 형식 등록(read · write · sample), 가져오기 창의 형식 제안, 기본 형식 추가(VOC · CSV · COCO 학습용 · YOLO pose) | 사내 JSON을 흉내 낸 형식으로 가져오기 → write로 풀어 학습 | 가능 |
| **6** 컨테이너 | 같은 선언으로 컨테이너 실행, 이미지 만들기 · 레지스트리 · 다이제스트, 서버 능력으로 배정 (EXECUTION_PLAN 7장 5단계를 대신함) | 이 PC의 Docker Desktop에서 YOLO11n 학습, 사내 이미지를 `image`로 가리켜 학습. 원격 Linux 서버는 그 서버에서 | 가능 (GPU 넘기기 · Linux 서버는 확인 필요) |
| **7** 파일 속성 | 마스크 PNG · 깊이 지도 같은 파일 라벨, 의미 분할 · 회전 박스 | 작은 마스크 데이터로 가져오기 → 학습 → mIoU | 가능 |

순서의 이유:

- 1 · 2는 처음 요청인 "돌아가는 것만 등록"이다. 1은 Hub만 고쳐 지금 노드에서 늦게 드러나는 실패를 앞으로 당긴다.
- 3이 4 · 5보다 먼저다. 팀 데이터 · 팀 모델이 늘어날수록 "같은 자로 잰다"가 비교의 바탕이 된다.
- 6은 2 위에 얹는다. 시험 실행이 컨테이너에서도 같은 절차로 돌면 된다. 이 PC에서 먼저 확인하고 원격 Linux 서버로 넓힌다.

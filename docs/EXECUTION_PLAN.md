# 실행 기반 계획 — 모델 템플릿 · 환경 · 저장 위치

0.5.0의 학습은 "Ultralytics YOLO를, 노드가 자동으로 만든 환경에서, 데이터가 있는 그 노드에서" 돌리는 한 가지 경우만 된다.
이 문서는 그 세 고정값을 각각 고를 수 있는 것으로 바꾸는 계획이다. 아직 구현하지 않았다.

| 지금 고정된 것 | 바꾸려는 것 | 장 |
|---|---|---|
| 학습 코드 = Ultralytics YOLO | **모델 템플릿**: 사내 학습·평가·추론 코드를 등록해 골라 쓴다 | 2 |
| 환경 = 노드가 자동 설치한 가상환경 | **환경**: 자동 설치 / Docker 이미지 / 서버에 이미 있는 환경 중에서 고른다 | 3 |
| 데이터 = 학습하는 노드의 디스크 | **저장 위치**: 노드 폴더 / NAS / 별도 데이터 서버 / S3, 등록과 학습 모두 | 4 |

원칙은 그대로다. Hub에는 ML 라이브러리가 없고, 기본 설치는 가볍고, 무거운 것(Docker, S3 라이브러리)은 쓰는 사람만 켠다.

## 1. 전체 그림

학습을 시작할 때 고르는 것이 네 가지가 된다.

```
릴리스 (무엇으로)  +  모델 템플릿 (어떤 코드로)  +  환경 (어디에 깔린 무엇으로)  +  노드 (어느 서버에서)
   └ 4장                └ 2장                         └ 3장                          └ 자동 또는 지정
```

- 템플릿을 고르면 그 템플릿의 **기본 환경**이 함께 선택된다. 바꿀 수 있다.
- 노드는 "그 환경을 쓸 수 있고 그 데이터를 읽을 수 있는(또는 받아 올 수 있는)" 서버 중에서 자동으로 정하거나 사람이 지정한다.
- 학습 실행(Run)은 네 가지를 모두 버전까지 기록한다: 릴리스, 템플릿 버전(코드 해시), 환경(이미지 다이제스트 또는 설치된 패키지 목록), 노드. "같은 설정으로 다시 실행"이 같은 코드와 같은 환경으로 돌아간다.
- 계보는 `모델 → 학습 실행 → (릴리스, 템플릿 버전, 환경)`으로 늘어난다.

## 2. 모델 템플릿

### 2.1 무엇인가

**모델 템플릿 = 한 종류의 모델을 다루는 코드 묶음.** 학습·평가·추론·내보내기 진입점, 화면에 보일 설정 항목, 기본 환경을 한 파일에 선언한다.
예: "Ultralytics YOLO"(내장), "사내 RT-DETR", "불량 분류기".

지금의 Ultralytics YOLO도 같은 형식의 **내장 템플릿**으로 옮긴다. 내장과 사내 템플릿이 같은 경로로 실행되므로 특별 취급이 없다.

### 2.2 선언 파일

템플릿 폴더의 `badamoa.toml` 하나다 (TOML은 Python 표준 라이브러리로 읽으므로 의존성이 늘지 않는다).

```toml
name    = "inhouse-rtdetr"
title   = "사내 RT-DETR"
version = "1.2.0"
task    = "detect"            # detect | segment | classify
data_format = "coco"          # BADAMOA가 릴리스를 이 형식으로 풀어 준다: yolo | coco | imagefolder | manifest

[environment]
default      = "rtdetr-cu121"       # Hub에 등록된 환경 이름 (3장)
requirements = "requirements.txt"   # "자동 설치" 환경을 만들 때 쓰는 목록

[entrypoints]                 # 있는 것만 적는다. train만 있어도 된다
train   = "python train.py --config {config}"
eval    = "python eval.py --config {config}"
predict = "python predict.py --config {config}"
export  = "python export.py --config {config}"

[params.model]                # 학습 대화상자의 입력 항목이 된다
type = "string"
choices = ["r18", "r50", "r101"]
default = "r18"
label = "백본"

[params.epochs]
type = "integer"
default = 72
```

`data_format = "manifest"`는 변환 없이 이미지 경로·split·박스를 적은 JSON Lines 파일만 받는 방식이다. 자체 데이터 로더가 있는 코드용이다.

### 2.3 코드가 지켜야 할 약속

0.5.0에서 YOLO 스크립트에 쓴 약속을 그대로 일반화한다. 코드는 BADAMOA를 import하지 않는다.

| 방향 | 내용 |
|---|---|
| 입력 | `{config}` 자리에 JSON 파일 경로가 들어온다: 데이터 경로, 출력 폴더, 장치(`cpu` / `0` / `0,1`), 클래스 이름, 사용자가 고른 설정값. 평가·추론은 여기에 가중치 경로가 더해진다 |
| 진행 보고 | 표준 출력에 `@@badamoa {JSON}` 한 줄: `info`(라이브러리 버전·장치), `epoch`(epoch 번호와 지표) |
| 결과 | `result` 한 줄: 학습은 가중치 파일 경로·최종 지표·클래스별 지표, 평가는 지표, 추론은 예측 파일 경로 |
| 그 밖의 출력 | 전부 작업 로그가 된다 |

- 보고용 한 파일짜리 도우미(`badamoa_report.py`, 의존성 없음)를 템플릿에 복사해 넣어 준다: `report.epoch(3, 72, {"map50_95": 0.41})`.
- 지표 이름은 자유지만 `map50_95, map50, precision, recall`(검출), `top1, f1`(분류)을 쓰면 표와 타일에 바로 나온다. 나머지는 그래프에만 나온다.
- 코드를 고칠 수 없는 경우를 위해 "결과 CSV를 읽어 지표로 보고"하는 방식을 뒤에 추가할 수 있다. 처음에는 넣지 않는다.

### 2.4 등록과 전달

| 방법 | 동작 | 맞는 경우 |
|---|---|---|
| 올리기 | `badamoa template push ./my-trainer` — 선언을 검사하고 폴더를 묶어 Hub에 저장. 노드는 Hub에서 받아 해시로 캐시 | 기본. 노드가 Hub에만 닿으면 되므로 폐쇄망에서도 된다 |
| Git | 저장소 주소와 커밋을 등록. 노드가 직접 clone | 노드가 사내 Git에 닿을 때 |
| 이미지에 포함 | Docker 이미지 안의 경로를 지정 | 코드와 환경을 한 이미지로 굳혀 쓸 때 |

- `badamoa template init --task detect`가 뼈대(선언 파일, 약속을 지키는 `train.py` 예시, 보고 도우미)를 만들어 준다.
- 올릴 때마다 **버전**이 쌓이고, 학습 실행은 쓴 버전의 코드 해시를 기록한다. 같은 버전 번호로 다른 코드를 올리면 거부한다.
- 화면: Develop 아래 **템플릿** 목록(이름 · 태스크 · 버전 · 지원 진입점 · 기본 환경 · 이 템플릿으로 만든 모델 수).

### 2.5 평가·추론·내보내기에 쓰이는 방식

모델 버전은 **자신을 만든 템플릿 버전을 기억한다.** 그 모델을 평가·추론·내보낼 때는 같은 템플릿의 진입점을 쓰므로, 학습 코드와 추론 코드의 전처리가 어긋나지 않는다.

| 진입점 | 작업 | 결과가 가는 곳 | 시기 |
|---|---|---|---|
| `train` | 릴리스 → 가중치 | 학습 실행, 모델 버전 | 1C |
| `eval` | 모델 + 릴리스(split) → 지표 | 모델의 **평가 기록**. 서로 다른 데이터로 학습한 모델도 같은 릴리스로 평가해 공정하게 비교 | 1C |
| `predict` | 모델 + 이미지 묶음 → 예측 | 라벨 개정(`autolabel:<모델>@<버전>`) 또는 샘플 테스트 화면 | Phase 3·4 |
| `export` | 모델 → ONNX·TensorRT | 모델의 내보낸 파일 | Phase 4 |

진입점이 없는 기능은 그 모델에서 버튼이 비활성으로 보인다("이 템플릿에는 평가 코드가 없습니다").

## 3. 환경

### 3.1 세 가지 방식

| 방식 | 선언 | 실행 | 맞는 경우 |
|---|---|---|---|
| 자동 설치 (지금) | 패키지 목록 | 노드가 처음 쓸 때 uv로 가상환경을 만든다. PyTorch는 드라이버에 맞는 빌드 | 준비 없이 바로, Windows 노드 |
| Docker 이미지 | 이미지 이름·태그 | 노드가 컨테이너로 실행. 배정받은 GPU만 넘기고 데이터·작업 폴더를 마운트 | 환경을 고정해 여러 서버에서 똑같이, 폐쇄망 |
| 기존 환경 | 서버에 있는 Python 경로 (conda·venv) | 그 Python으로 실행 | 이미 잘 돌아가는 환경이 서버에 있을 때 |

환경은 Hub에 **이름으로 등록**하고(예: `yolo-auto`, `rtdetr-cu121`), 템플릿은 기본 환경의 이름만 가리킨다. 환경과 코드가 따로 버전을 가지므로 같은 코드를 다른 환경에서 돌려 볼 수 있다.

### 3.2 노드와의 관계

- 환경마다 **어느 노드에서 쓸 수 있는지**가 표시된다: 준비됨 / 준비 가능(이미지를 받거나 설치하면 됨) / 불가(OS가 다름, Docker 없음).
- "미리 준비" 작업을 둔다. 첫 학습이 설치나 이미지 받기를 기다리지 않게 한다.
- 스케줄러는 환경을 쓸 수 있는 노드에만 배정하고, 대기 사유에 "이 환경을 쓸 수 있는 노드가 없음"을 표시한다.
- 기존 환경은 노드마다 경로가 다를 수 있으므로 노드별로 경로를 적는다.

### 3.3 Docker 방식에서 처리할 것

- GPU는 `CUDA_VISIBLE_DEVICES` 대신 컨테이너에 넘기는 장치 목록으로 제한한다.
- 학습 데이터는 원본을 가리키는 링크이므로, 원본 폴더도 같은 경로로 읽기 전용 마운트한다.
- 컨테이너 안의 사용자를 노드 사용자로 맞춰 결과 파일의 소유자가 root가 되지 않게 한다.
- 취소는 프로세스 종료가 아니라 컨테이너 중지로 한다.
- 실행 기록에 이미지 다이제스트를 남긴다.
- Linux 노드 전용이다 (Docker + NVIDIA Container Toolkit). Windows 노드에서는 선택지에 나오지 않는다.

## 4. 저장 위치

### 4.1 등록

등록은 방식과 상관없이 "그 데이터를 읽을 수 있는 노드가 훑어서 해시·크기·라벨·썸네일만 Hub에 올린다"이다. Hub는 이미지 파일을 받지 않는다.

| 위치 | 등록하는 노드 | 추가로 적는 것 | 상태 |
|---|---|---|---|
| 노드 폴더 | 그 서버 | 없음 | 됨 (0.4.0) |
| 별도 데이터 서버 | 데이터 서버에 설치한 노드 (GPU 불필요) | 없음 | 등록은 됨 |
| NAS | NAS를 마운트한 아무 노드 | 서버별 마운트 경로 | 계획 |
| S3 호환 | 버킷에 닿는 아무 노드 | 버킷·경로·자격 증명 | 계획 |

S3는 등록할 때 모든 객체를 한 번 내려받아 해시와 썸네일을 만든다(저장하지 않고 버린다). 이미지를 내용 해시로 식별하기 때문이다.

### 4.2 학습할 때 읽기

학습 노드는 이미지마다 아래 순서로 읽을 곳을 찾는다.

1. 내 디스크에 등록된 폴더 → 그대로 (지금 방식)
2. 내가 마운트한 NAS → 내 마운트 경로로 바꿔서. 복사 없음
3. 내 캐시 → 전에 받아 둔 것. 해시로 식별하므로 다시 받지 않는다
4. 없음 → S3에서 직접 받거나, 데이터 서버에서 Hub를 거쳐 받아 캐시에 넣는다

- 노드는 Hub로 나가는 연결만 쓰므로 서버 간 전송은 **Hub를 거친다.** 수백 GB 데이터는 Hub의 네트워크 속도에 묶이니 NAS나 S3가 맞다. 서버 간 전송은 그런 인프라가 없을 때의 방법이다.
- 캐시는 노드별 용량 한도를 두고 오래 안 쓴 것부터 지운다.
- 학습 노드 선택: 바로 읽을 수 있는 노드 → 캐시에 가장 많이 가진 노드 → 그 밖의 GPU 노드 순으로 고르고, 받아 와야 하는 양을 시작 전에 보여 준다.

## 5. 데이터 모델 변경

| 표 | 내용 |
|---|---|
| `templates` | 이름, 버전, 태스크, 선언(JSON), 코드 묶음 해시 또는 Git 주소·커밋, 내장 여부 |
| `environments` | 이름, 방식(auto / docker / python), 내용(패키지 목록 · 이미지 · 경로), 지원 OS |
| `node_environments` | 노드별 상태(준비됨 / 준비 가능 / 불가)와 경로·다이제스트 |
| `runs` (추가) | 템플릿 버전, 환경, 환경 다이제스트 |
| `model_versions` (추가) | 만든 템플릿 버전 |
| `evaluations` | 모델, 릴리스, split, 지표, 클래스별 지표, 작업 |
| `storage_locations` (추가) | 종류(node / shared / s3), 설정 |
| `location_mounts` | 공유 위치의 서버별 마운트 경로 |
| `item_locations` | 이미지가 있는 위치들. 지금은 이미지당 위치 하나인 것을 여러 개로 |

기존 DB는 시작할 때 자동으로 옮긴다: 지금의 위치는 `node` 종류로, 지금의 YOLO 학습 실행은 내장 템플릿과 `yolo-auto` 환경을 가리키게 한다.

## 6. 권한

사내 코드를 등록한다는 것은 노드에서 임의의 코드를 실행한다는 뜻이다.

- 템플릿·환경·저장 위치의 등록과 수정은 **관리자**만 한다. 멤버는 등록된 것을 골라 쓴다.
- 등록·수정·사용은 모두 감사 로그에 남는다.
- S3 자격 증명과 레지스트리 자격 증명은 Hub에 저장하고, 그것이 필요한 작업에만 넘긴다. 화면과 로그에는 나오지 않는다.
- 자동 설치·기존 환경 방식의 코드는 Node Agent를 실행한 사용자 권한으로 돈다. 격리가 필요하면 Docker 방식을 쓴다.

## 7. 구현 순서

각 단계는 그것만으로 쓸 수 있는 상태로 끝낸다. 확인은 지금처럼 가볍게 한다(COCO128, 가장 작은 모델).

| 단계 | 내용 | 확인 방법 | 이 PC에서 확인 |
|---|---|---|---|
| **1** 템플릿과 환경의 틀 | 선언 형식, 내장 YOLO 이전, 템플릿 올리기·뼈대 만들기, 환경 등록(자동 설치 · 기존 환경), 학습 대화상자에서 템플릿·환경 선택과 설정 항목 자동 생성, 실행에 버전 기록 | 뼈대로 만든 작은 사내 템플릿을 올려 학습 → 모델 등록. YOLO는 전과 같이 동작 | 가능 |
| **2** 평가 | `eval` 진입점, 평가 작업, 모델의 평가 기록, 같은 릴리스로 평가한 모델끼리 비교 | YOLO 모델 두 개를 같은 릴리스로 평가해 비교 | 가능 |
| **3** 저장 위치의 틀과 NAS | 위치 찾기 단계, 이미지당 여러 위치, 공유 마운트 등록과 서버별 경로, 학습 노드 선택 | 노드 두 개를 띄우고 같은 폴더를 서로 다른 경로로 마운트한 것처럼 구성해 양쪽에서 학습 | 가능 (실제 NAS는 서버 검증 때) |
| **4** 서버 간 동기화 | 노드 캐시, Hub 경유 전송, 받아 올 양 미리 표시, 캐시 한도 | 데이터 노드와 학습 노드를 따로 띄워 학습 | 가능 |
| **5** Docker 환경 | 3.3의 항목 전부, "미리 준비" 작업 | Linux GPU 서버에서 공식 Ultralytics 이미지로 학습 | 불가 — Linux 서버 검증과 함께 |
| **6** S3 | 버킷 등록, S3에서 등록과 학습, 자격 증명 보관 | MinIO 또는 실제 버킷 | 엔드포인트가 있어야 함 |

`predict`와 `export` 진입점은 형식만 1단계에서 정해 두고, 실제로 쓰는 Phase 3(오토라벨)·Phase 4(내보내기·추론)에서 구현한다.

순서의 이유: 1은 2~6이 모두 기대는 틀이고(환경 선택과 템플릿이 같은 실행 코드를 고친다), 2는 1 위에서 작고 "모델 비교가 공정하지 않다"는 지금의 한계를 없앤다. 3·4는 이 PC에서 확인할 수 있고, 5·6은 외부 자원이 있어야 확인할 수 있어 뒤에 둔다.

## 8. 만들지 않는 것

- 템플릿마다 다른 화면. 설정 항목은 선언에서 자동으로 만든 입력 폼 하나다.
- 템플릿 마켓·공유 저장소. 사내용이므로 Hub에 올린 것이 전부다.
- 자체 이미지 빌드. Docker 이미지는 밖에서 만든 것을 이름으로 가리킨다.
- 노드끼리 직접 전송. 먼저 Hub 경유로 만들고, 속도가 문제가 되면 그때 추가한다.

## 9. 정해야 할 것

- 사내 학습 코드가 지금 어떤 형태인가 (스크립트 몇 개 / 설정 파일 기반 프레임워크 / 노트북). 2.3의 약속에 맞추는 데 드는 수정량이 달라진다.
- "미리 정해진 환경"이 Docker 이미지인가, 서버의 conda 환경인가. 뒤쪽이면 1단계만으로 쓸 수 있다.
- NAS·S3가 실제로 있는가. 없다면 5·6단계는 코드만 넣고 확인이 미뤄진다.
- 템플릿을 등록할 수 있는 사람을 관리자로 한정해도 되는가.
